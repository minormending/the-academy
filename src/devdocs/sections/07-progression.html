Progression and balance

This section covers everything that makes a student stronger over time: how much EXP a level costs, how a character's numbers are computed, how spells and stats are bought with points, how a student moves from Year 1 to Year 4, and how items and currencies feed into all of it. It also covers the one file every content author had to agree on, src/core/balance.ts.

A few terms first. A balance curve is a small function of level (for example refMatk(level)) that says what a number should be at that level. Base stats are the four numbers the player raises by hand (STR, DEX, INT, LUK). Derived stats are what the game actually uses (max HP, magic attack, crit rate, cooldown reduction…), computed from level, base stats, gear, passive spells and active buffs. SP (skill points) buy spell levels; AP (ability points) buy base stats. A job is the character class; in The Academy each job tier is a school Year, and moving up a tier is passing that Year.

balance.ts: the shared tuning contract

The game was built by ten agents working in parallel (see how it was built). The monster author, the five skill-tree authors and the progression author never saw each other's numbers while they worked, yet a level-30 Flamebinder still needs about three or four casts to kill a level-30 monster. That works because everyone tuned against the same reference curves, owned by the lead and marked "do not edit":

/** EXP needed to go from `level` to level+1. */
export function expToNext(level: number): number {
  return Math.floor(15 * Math.pow(level, 1.85) + 10);
}

/** Intended number of same-level normal kills per level. */
export function killsPerLevel(level: number): number {
  return 8 + Math.floor(level * 1.6);
}

/** Reference EXP for a normal monster of `level`. Bosses ~ 40x. */
export function refMonsterExp(level: number): number {
  return Math.max(3, Math.round(expToNext(level) / killsPerLevel(level)));
}

/** Expected player magic attack at `level` with on-level gear and INT-focused AP. */
export function refMatk(level: number): number {
  return 12 + 5 * level;
}

/** Reference single-target damage % of the level-appropriate primary skill (per hit line). */
export function refSkillPct(level: number): number {
  return level < 10 ? 140 : level < 25 ? 220 : level < 40 ? 300 : 450;
}

/** Expected damage of one hit line of the primary skill. */
export function refHit(level: number): number {
  return (refMatk(level) * refSkillPct(level)) / 100;
}

/** Normal monster HP: ~3-4 primary-skill casts. Bosses ~ 250x. */
export function refMonsterHp(level: number): number {
  return Math.round(refHit(level) * 3.5);
}

/** Monster touch damage at `level`. */
export function refMonsterTouch(level: number): number {
  return Math.round(8 + level * 4.5);
}

/** Expected player max HP / MP at level (before passives). */
export function refPlayerHp(level: number): number { return 60 + level * 20; }
export function refPlayerMp(level: number): number { return 40 + level * 24; }
// …
export const SP_PER_LEVEL = 3;
export const AP_PER_LEVEL = 5;

Advanced: the contract's invariants and where code departs from it
  • Only the lead edits balance.ts. Ownership rule 1 in ARCHITECTURE.md. Every other module reads it. A change here re-tunes monsters, quest rewards, the Trial Hall and stats calibration at once, so treat it as a global rebalance and replay a few levels in each Year afterwards.
  • Monsters derive from the curves, they don't copy numbers. mk() in monsters.ts:79 sets hp = round(refMonsterHp(lv) × hpMul), exp = round(refMonsterExp(lv) × expMul) and touchDamage = round(refMonsterTouch(lv) × touchMul), with per-monster multipliers in roughly the 0.8–1.3 band ARCHITECTURE.md asks for.
  • Comments that drifted. balance.ts says bosses are "~250x" HP; after the 25–50 pacing pass the Lich Archon uses refMonsterHp(48) × 200, and field bosses use 28–65× (they are mini-bosses). The killsPerLevel figure is design intent: real pacing also includes quest EXP, the above-level bonus and Trial Hall EXP.
  • The Year steps are deliberate. Monster HP jumps at 10/25/40 because players get stronger spells there. A student who stays a Year behind (no exam passed) hits a wall at those levels, which is the intended pressure to sit the Exam.
  • The ±15% target. ARCHITECTURE.md requires derived matk to land within ±15% of refMatk for an INT build with on-level gear. At level 10 with the Sage Wand the formula gives 63 against a reference of 62; at level 40 with the Inferno Staff, Runed Gloves, Mana Ring and Arcane Amulet it gives 223 against 212 (+5%).

EXP and levelling up

Progression subscribes to monster:killed in its constructor. Each kill grants the monster's exp scaled by the level difference:

/**
 * EXP multiplier for a kill: monsters ≥10 levels below the player give progressively less
 * (down to 10%); monsters above the player give a small bonus (up to +15%).
 */
export function killExpMultiplier(playerLevel: number, monsterLevel: number): number {
  const diff = playerLevel - monsterLevel;
  if (diff >= 10) return Math.max(0.1, 0.7 - (diff - 10) * 0.06);
  if (diff < 0) return 1 + Math.min(0.15, -diff * 0.05);
  return 1;
}

(Progression.ts:39.) Note the above-level bonus is capped at +15% (+5% per level, reached three levels up). The balance follow-up commit be584c4 lowered it from +30%, and the doc comment now says +15% as well.

gainExp handles multi-level jumps (a quest reward can cross several levels) and pays SP and AP for each level crossed:

  gainExp(amount: number) {
    amount = Math.floor(amount);
    if (!(amount > 0)) return;
    const s = this.state;
    if (s.level >= MAX_LEVEL) { s.exp = 0; return; }
    s.exp += amount;
    const startLevel = s.level;
    while (s.level < MAX_LEVEL && s.exp >= expToNext(s.level)) {
      s.exp -= expToNext(s.level);
      s.level += 1;
      s.sp += SP_PER_LEVEL;
      s.ap += AP_PER_LEVEL;
    }
    if (s.level >= MAX_LEVEL) s.exp = 0;
    if (s.level > startLevel) {
      this.cache = null;
      const d = this.derived();
      // EXP can still land after death (burn ticks, in-flight projectiles): don't revive via level-up.
      if (!this.dead) {
        s.hp = d.maxHp;
        s.mp = d.maxMp;
      }
      // …
      bus.emit('player:levelup', { level: s.level });
      this.refreshQuests();
      // Announce a new advancement only on the level-up that first crosses its required level.
      // …
      this.save();
    }
    this.changed();
  }

(Progression.ts:99.) state.exp is the EXP into the current level, not a lifetime total. MAX_LEVEL is 50 (constants.ts:19), and EXP is pinned to 0 there.

Advanced: levelling edge cases
  • Dead students can still level. A burn tick or an in-flight projectile can kill a monster after the player died. The level is granted, but HP/MP are not refilled, so a level-up never revives the player behind the death prompt's back.
  • The advancement notice fires once. It checks whether any child job's requiredLevel lies in (startLevel, level], so a student who hovers around level 25 is told about the Year 3 Exam only on the level-up that first reaches it.
  • Every level-up saves. So does every other milestone (see saves); the 30 s autosave is only a safety net.
  • EXP from anything goes through gainExp. Quests, the Trial Hall bonus and kills all use it, so SP/AP payouts and the quest refresh can't be skipped by a new EXP source.

Derived stats

progression/stats.ts is pure math with no services, so the save system can use it too (to fill a new character's HP and clamp a loaded one). The base formula:

/**
 * Base formula (before equipment / passives / buffs).
 * Calibrated so INT-focused AP (≈4 INT + 1 LUK per level) + on-level gear gives
 * matk ≈ refMatk(level) = 12 + 5L (base ≈ 6.9 + 4.4L; gear supplies ≈ 5 + 0.6L).
 */
export function baseDerived(state: PlayerState): DerivedStats {
  const L = Math.max(1, state.level | 0);
  const { str, dex, int, luk } = state.base;
  return {
    maxHp: 55 + 19 * L + str,
    maxMp: 36 + 20 * L + int * 0.4,
    matk: int * 0.9 + luk * 0.3 + L * 0.5,
    def: L * 0.3 + str * 0.2,
    critRate: 0.05 + Math.max(0, luk - 6) * 0.001,
    critDmg: 0.5,
    mastery: 0.45 + Math.max(0, dex - 4) * 0.002,
    speed: 200,
    jump: 560,
    hpRegen: 5 + L * 0.6 + str * 0.2,
    mpRegen: 6 + L * 0.9 + int * 0.1,
    mpShield: 0,
    dmgAll: 0,
    // … dmgFire, dmgIce, dmgLightning, dmgHoly, dmgShadow: 0
    castSpeed: 0,
    cdr: 0,
  };
}

(stats.ts:21.) INT is by far the most valuable base stat: 0.9 matk per point plus MP and MP regen. LUK adds a little matk and 0.1% crit per point above 6; DEX raises mastery (the low end of the damage roll, see combat math); STR adds HP, DEF and HP regen.

Then every stat modifier ({ stat, add?, mul? }) is folded in:

/** final = (base + Σadd) × (1 + Σmul), then rounded/clamped. */
export function applyModifiers(base: DerivedStats, mods: StatModifier[]): DerivedStats {
  // … sum every add and every mul per stat (non-finite values ignored)
  const out = { ...base };
  for (const k of Object.keys(base) as DerivedStatKey[]) {
    out[k] = (base[k] + (addSum[k] ?? 0)) * (1 + (mulSum[k] ?? 0));
  }
  for (const k of INT_STATS) out[k] = Math.max(0, Math.floor(out[k]));
  out.maxHp = Math.max(1, out.maxHp);
  out.maxMp = Math.max(1, out.maxMp);
  out.matk = Math.max(1, out.matk);
  out.speed = Math.max(60, out.speed);
  out.jump = Math.max(200, out.jump);
  out.critRate = clamp(out.critRate, 0, 1);
  out.critDmg = Math.max(0, out.critDmg);
  out.mastery = clamp(out.mastery, 0, 0.95);
  out.mpShield = clamp(out.mpShield, 0, 0.9);
  out.castSpeed = clamp(out.castSpeed, 0, 0.75);
  out.cdr = clamp(out.cdr, 0, 0.6);
  return out;
}

(stats.ts:68.) The modifiers come from three places:

  • Equipment and learned passives: persistentModifiers(state) (stats.ts:49) walks the equipped items' equip.modifiers and calls each learned passive skill's passive(level).
  • Active buffs: Progression.derived() asks the skill system for getBuffModifiers() and passes them as extra (Progression.ts:63).

Worked example. A level-10 student who always pressed Auto has INT 46 and LUK 15, so base matk = 46 × 0.9 + 15 × 0.3 + 10 × 0.5 = 50.9. With the Sage Wand (+13 matk): (50.9 + 13) × 1 = 63.9, floored to 63. refMatk(10) is 62. A buff granting mul: 0.1 would make it floor(63.9 × 1.1) = 70.

Advanced: caching, additive multipliers and failure modes
  • Cached until invalidated. derived() returns the cached object until invalidate() is called. Learning a spell, equipping, unequipping, allocating AP and respec all invalidate; the skill system calls progression.invalidate() whenever a buff starts or ends. A new source of modifiers must do the same, or its effect shows up only after something unrelated invalidates.
  • Multipliers add, they don't compound. Two +10% effects give ×1.2, not ×1.21. That keeps stacking predictable and makes the order of modifiers irrelevant.
  • Fractional stats stay fractional. Only the eight INT_STATS are floored; crit rate, mastery, cast speed, CDR and the dmg* bonuses keep their decimals.
  • derived() also clamps vitals. If max HP drops (unequipping a robe, a buff ending), current HP and MP are cut to the new max as a side effect of the next derived() call.
  • A throwing passive can't break stats. Each passive(lv) call is wrapped in try/catch, and if computing with buffs throws, derived() falls back to computing without them. Unknown stat keys in a modifier are skipped (m.stat in base).

Advanced: where the Exam gate actually lives
  • advanceJob does not check the Exam. It only checks parent and level, as its comment says. The gate is enforced by the callers: the Professor script only offers "Make me a…" after the exam quest is turned_in, and availableAdvancements (used by the UI) filters on it. The debug console's arcana.job('pyromancer') relies on this to skip ahead. If you add another path that promotes a student, gate it the same way.
  • No transfers. Once declared, the branch is fixed: only children of the current job can be advanced to, and every other School's exam fails canAcceptQuest on requiredJobBranch. The shop's "Sell junk" button relies on this to treat other Schools' exam materials as junk.
  • Lineage means old spells stay. Spells are learnable for any job in the lineage, so a Year 4 student can still spend SP on Year 1 and Year 2 spells.
  • Adding a School means a new Branch in types.ts, three JobDefs, entries in all four School maps, a Professor NPC and script lines, and two exam quests in JOB_ADVANCEMENT_QUESTS. The recipes section walks through it.

Respec: unlearning a Year

Phase 5 added a way to undo build mistakes one Year at a time. The Spellbook (K by default) has an Unlearn Year button on each unlocked Year tab; it costs one Tome of Unlearning, sold by Bram for 2,500 mesos or at the Merit Exchange for 150 Merits.

  respecTier(tier: JobTier): number {
    const job = Registry.jobLineage(this.state.job).find(j => j.tier === tier);
    if (!job) return 0;
    let refund = 0;
    for (const sk of Registry.skillsForJob(job.id)) {
      const lv = this.state.skills[sk.id] ?? 0;
      if (lv <= 0) continue;
      // The free starting Arcane Bolt level is not refundable (it was never bought with SP).
      const free = sk.id === 'app_arcane_bolt' ? 1 : 0;
      refund += Math.max(0, lv - free);
      if (free) this.state.skills[sk.id] = free; else delete this.state.skills[sk.id];
      if (!free) this.state.hotbar = this.state.hotbar.map(e => (e === sk.id ? null : e));
    }
    if (!refund) return 0;
    this.state.sp += refund;
    this.invalidate();
    // … log "You unlearned your <job> spells (+N SP)."
    return refund;
  }

(Progression.ts:152.) The window takes the tome first, then calls respecTier, and gives the tome back if nothing was refunded (skillsWindow.ts:184). The button needs two clicks: the first arms it and shows the refund, the second (if nothing changed in between) confirms.

Advanced: respec invariants
  • SP is conserved. Every refunded level was bought with exactly one SP, except the free Arcane Bolt level, which stays learned. A student can't farm SP by unlearning.
  • Dependants go too. Because a whole Year is unlearned, a requires chain inside that Year can't be left half-satisfied. Requirements never cross Years in the current data; if you add one, unlearning the earlier Year would leave a later spell learned without its prerequisite (harmless at cast time, but surprising in the spellbook).
  • Hotbar and passives. Unlearned spells leave the hotbar; passives disappear from derived() through the invalidate() call.

Academy Merits

Academy Merits are a second currency stored in state.merits (optional in PlayerState, so pre-Phase 5 saves load with 0). They are earned in the Trial Hall (meritsForWave(n) = 2 + 2n, doubled on every fifth wave, so ten waves pay 164), through the 1,000-Merit graduation award and as the reward for Academy Honors, and they are spent only at Bram's Merit Exchange.

Academy Honors

Academy Honors are the game's achievements: 60 of them in six categories (Studies, Schools, Field Work, Trial Hall, Academy Life and Secret). Each pays Merits once and some unlock a title that shows under the student's name tag. They are all data in honors.ts: an HonorDef has a measure(view) and a target(view), both pure functions of the saved PlayerState plus a bag of counters, and the honor is earned when measure >= target. The same two functions draw the progress bars in the Honors window (O by default, or the Honors quick button), so the bar and the award can't disagree.

The saved shape is small (types.ts:460): done maps an honor id to the time it was earned, counters holds tallies the save does not otherwise remember (kills per zone and per monster, casts, deaths, visited maps, people talked to, Merits earned and spent, the fastest Lich Archon kill), and title is the chosen title. HonorsSystem is created by GameScene next to Progression (GameScene.ts:72), subscribes to the bus to keep the counters, and runs evaluate() on a throttle: soon after something changed, and at least every couple of seconds.

Advanced: invariants of the honors system
  • An honor can never pay twice. evaluate() writes done[id] before it grants anything (HonorsSystem.ts:243), so a handler that throws or a re-entrant player:changed finds the honor already marked. Granting Merits goes through addMerits, which emits player:changed; a granting flag keeps that from being counted as Merits earned by play.
  • Old saves are backfilled. A save with no honors field (written before the system existed) gets counters derived from what it does know: level, job, exams, graduation, quest kill counts, the current map and Merits. Whatever that already satisfies is granted in one summary banner instead of a banner per honor. repairHonors (SaveSystem.ts:373) deliberately leaves the field undefined when it is absent so the system can tell a legacy save from a new one, keeps unknown honor ids (they may come from a newer build) and clamps counters.
  • Ids are save data. Like skills and maps, an honor id is never renamed, for the reasons in Why ids never get renamed.
  • Honors can depend on content. requiresMaps hides an honor until its maps exist (availableHonors()), so the branch-zone honors are only offered when those zones are in the build.
  • Banners are rationed. Honor banners wait behind level-up, exam and map-name banners and appear one at a time.

Inventory

  • 48 stacks (MAX_INVENTORY_STACKS). Consumables stack to 100 (Return Scrolls 50), most etc items to 200 (tomes and trophies 10), equipment to 1. roomFor answers "how many more fit"; canFit simulates several adds after some removals, which is how quest turn-in checks room before it changes anything.
  • Potions on the hotbar. Hotbar entries are skill ids or "item:<id>". A new character has Red and Blue Potions on keys 1 and 2 of both hotbar pages, and setHotbar lets the same potion sit once per page. When the assigned potion runs out, useItem falls back to the strongest potion of the same kind that you do have (White, Orange, Red for HP; Mana Elixir, Blue for MP) and says so once (Progression.ts:467).
  • Item cooldowns are per item (cooldownMs: 300 ms for potions, 1 s for the Elixir and the Return Scroll, 1.5 s for the Power Elixir). A potion that would heal nothing is refused and not consumed.

Regeneration, death and respawn

Progression.update runs first in every frame. Every 5 s it applies one regen tick of hpRegen/mpRegen, tripled on a safe map (the campus), and every 30 s it autosaves (Progression.ts:737).

/** Fraction of the current level's EXP requirement lost on death. */
export const DEATH_EXP_PENALTY = 0.05;

/** EXP lost when dying at this level/exp (never drops below 0 EXP, no penalty at max level). */
export function deathExpLoss(level: number, exp: number): number {
  if (level >= MAX_LEVEL) return 0;
  return Math.max(0, Math.min(exp, Math.floor(expToNext(level) * DEATH_EXP_PENALTY)));
}

(stats.ts:8.) Dying at level 10 costs up to 53 EXP; at level 40, up to 690. A student never loses a level. respawn() applies the penalty, sets HP to 50% of max and MP to at least 50%, and emits player:revived; GameScene then moves the player to campus.

Advanced: death invariants
  • While dead, nothing heals. heal, regen ticks, useItem and spendMp all refuse while dead, and loseHp ignores further hits, so a burn tick can't fire player:died twice.
  • A save written while dead is repaired on load. If the tab is closed at the death prompt, repairState applies the same penalty and sends the student to campus (see saves), so reloading is never a way to skip the penalty or to revive on a hostile map.

Advanced: tuning safely
  • Tune multipliers, not curves. To make one zone faster, change the monsters' expMul/hpMul (what the 25–50 pass did) rather than balance.ts, which moves every zone and every quest reward at once.
  • Quest EXP follows the curve. All quest rewards are xp(level, fraction) of expToNext, so a curve change rescales them automatically; a hand-written EXP number would not.
  • Watch the Year boundaries. The monster HP step at 10/25/40 assumes the student has the new Year's spells. If you lower a School's Year 2 primary, levels 10–14 feel it first.
  • There is no balance test suite. Pacing was checked by playthrough QA (Phase 5 levels 1–25, Phase 7 levels 25–50 per School). The charts in this section are the quickest way to see a curve change before playing.
