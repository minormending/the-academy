The DOM UI

Everything you click in The Academy is plain HTML. The HUD, the hotbar, the Spellbook, the shop, the NPC dialog box and the title menu are DOM elements inside one <div id="ui-root"> that sits on top of Phaser's <canvas>. Only things that live in the world are Phaser objects: floating damage numbers (DamageNumbers.ts) and the name tags under the player and NPCs (NameTag.ts). They move with the camera and sort by depth with the sprites, so they belong on the canvas.

This section covers src/ui/ (agent A8 in the original build, plus the pixel pass "PX5"). Terms used throughout:

  • overlay: the #ui-root element, laid out at the game's logical 1280×720 and CSS-scaled to cover the canvas exactly.
  • UIRoot: the class that builds the overlay for a game session. It implements the IUI service, so GameScene sees it as services.ui (see Architecture).
  • UICtx: a small context object handed to every UI component (services, scaler, tooltip, drag manager, persisted layout, sfx(), log(), window open/toggle).
  • signature: a string a window computes from the state it draws. Unchanged signature means no re-render.

UIRoot: construction, bus, frame

GameScene creates the UI last of all services (s.ui = new UIRoot(this, s)) and calls s.ui.update(time, delta) at the end of every frame. The constructor follows the project rule that constructors may build DOM and subscribe to the bus but must not call other services, because the services object is still being filled in. It finds or creates #ui-root, makes the scaler, tooltip and drag manager, builds the UICtx, then the HUD pieces, the windows, the dialog, shop, death prompt and credits roll (UIRoot.ts:82). Construction order is the DOM order, so it is also the stacking order for elements without a z-index.

Every bus subscription goes through one wrapper that catches handler errors and remembers the unsubscribe function:

  private on<K extends keyof GameEvents>(ev: K, fn: (p: GameEvents[K]) => void) {
    this.unsubs.push(bus.on(ev, (p) => { try { fn(p); } catch (e) { console.warn(`[ui] ${String(ev)} handler failed`, e); } }));
  }

(UIRoot.ts:137). The subscriptions (UIRoot.ts:141) map game events to UI reactions:

update() (UIRoot.ts:357) runs the first-frame start() (welcome line, saved volumes, auto-open Help for a new character), re-checks the scaler, turns EXP deltas into a single coalesced "+N EXP" line, ticks the HUD and every window, and then decides whether gameplay input must be blocked. The whole body is in a try; errors are logged at most once every 2 s, so a broken window can never stop the game loop.

Blocking gameplay input

Most windows do not pause anything: you can fight with the Spellbook open, as in MapleStory. Only a conversation, a shop, the credits roll or a focused text field take the keyboard away from the game:

  private syncInputBlock() {
    const want = this.dialog.isOpen || this.shop.isOpen || this.credits.isOpen || isTextInput(document.activeElement);
    if (want === this.blocked) return;
    this.blocked = want;
    try { this.services.game.setInputBlocked(want); } catch { /* ignore */ }
  }

(UIRoot.ts:350). On the other side, GameScene.setInputBlocked disables Phaser's global key capture (so typed characters reach the input field), resets held keys and turns off player control:

  setInputBlocked(blocked: boolean) {
    this.inputBlocked = blocked;
    const kb = this.input.keyboard!;
    if (blocked) { kb.disableGlobalCapture(); kb.resetKeys(); } else { kb.enableGlobalCapture(); }
    this.s.player.setControlEnabled(!blocked && !this.transitioning);
  }

Window keys

keyDown (UIRoot.ts:243) is a window listener. Its order of precedence: an open Controls window that is capturing a key wins (controlsClaimKey); a focused text field only gets Esc (blur); the death prompt and credits roll swallow everything; an open dialog handles Esc, Enter/Space and digit keys. Otherwise the key is looked up in the rebindable bindings (Input): Esc or the menu action closes the topmost open window (highest z) or opens the menu; the other actions toggle Spellbook, Inventory, Character, Assignments, Help and the minimap. Key names in UI text always come from keyLabel(getBinding(action)), never a hard-coded letter.

Keeping the overlay on the canvas

Phaser runs with scale: { mode: Phaser.Scale.FIT, autoCenter: CENTER_BOTH } (main.ts:28): the 1280×720 canvas is scaled to fit the window and centred, leaving bars on two sides. The overlay has to follow. UIScaler (scaler.ts:15) sizes #ui-root to the logical 1280×720 once, sets transform-origin: 0 0, and on every change copies the canvas rectangle onto it as a left/top plus a uniform scale():

  apply() {
    const canvas = this.game.canvas;
    if (!canvas) return;
    const r = canvas.getBoundingClientRect();
    if (r.width < 1) return;
    const parent = (this.root.offsetParent as HTMLElement | null) ?? document.body;
    const p = parent.getBoundingClientRect();
    const k = r.width / GAME_WIDTH;
    const left = r.left - p.left + (parent.scrollLeft || 0);
    const top = r.top - p.top + (parent.scrollTop || 0);
    const key = `${left.toFixed(1)},${top.toFixed(1)},${k.toFixed(4)}`;
    if (key === this.last) return;
    // …
    st.transform = `scale(${k})`;
  }

(scaler.ts:45). It is triggered by window resize, Phaser's Scale.Events.RESIZE, a ResizeObserver on the canvas, and a cheap poll from update() every 300 ms, because the margins that autoCenter adds do not fire the observer. The cache key means an unchanged layout costs one getBoundingClientRect.

Because all UI code works in logical pixels, anything that reads mouse positions converts first: scaler.toLogical(clientX, clientY) divides by k. Window dragging, the drag ghost and tooltip placement all use it. In style.css the root itself has pointer-events: none and its children auto, so empty overlay space never steals clicks from the canvas.

Building DOM: dom.ts and context.ts

There is no framework. dom.ts provides h(tag, props, ...children), a hyperscript-style builder: class, style (string or object), text, onxxx listeners and data-*/aria-* attributes, with null/false children skipped. A window title bar is typical:

    this.titleBar = h('div', { class: 'ax-win-title' }, h('span', { class: 'ax-win-gem' }), this.titleText, this.titleExtra, closeBtn);
    this.body = h('div', { class: 'ax-win-body' });
    this.el = h('div', { class: `ax-window ${opts.className ?? ''}`, style: `width:${opts.width}px;display:none;` }, this.titleBar, this.body);

(window.ts:38). The rest of dom.ts is small and used everywhere: setText/toggleClass that only touch the DOM when the value changes, loadJson/saveJson that swallow storage errors, number and time formatters, cssColor/shade for turning 0xRRGGBB data colours into CSS, safe(fn, fallback) for calls into other services, and isTextInput.

context.ts defines UICtx and Layout, the persisted UI preferences in localStorage["arcana-ui-layout-v1"]: window positions (pos:<id>) and flags such as the minimap toggle, the Spellbook sort and per-character "help seen" and "credits seen". session.ts holds two module-level flags that cross the Title → Game boundary: markNewCharacter() (so the HUD auto-opens Help once) and markReturnToSelect() (so Quit to Title lands on Character Select).

Windows: frame, z-order and dragging

Every window extends UIWindow (window.ts:20). The base class owns the frame (title bar with a gem, title text, an extra slot such as the SP pill, a close button), open/close with ui_open/ui_close sounds, persistent position, and the render loop. Subclasses implement render() and usually signature():

  tick(time: number, delta: number) {
    if (!this.isOpen) return;
    if (this.dirty) {
      this.dirty = false;
      let sig: string;
      try { sig = this.signature(); } catch { sig = `x${++sigCounter}`; }
      if (sig !== this.lastSig) {
        this.lastSig = sig;
        try { this.render(); } catch (e) { console.warn(`[ui] ${this.id} render failed`, e); }
        // Content height can change (tabs, dialog options): keep the whole window above the HUD.
        if (!this.dragOff) this.clampIntoView('v');
      }
    }
    try { this.frame(time, delta); } catch { /* never throw in update */ }
  }

(window.ts:86). Two levels of laziness: a window only checks its signature when something marked it dirty (a bus event via markAllDirty(), or its own button handler via invalidate()), and only rebuilds its DOM when the signature differs. Signatures are usually a JSON.stringify of the state slices the window shows, for example the inventory's [tab, inventory, mesos, level, job]. render() rebuilds the body with replaceChildren; per-frame work that must not rebuild (the dialog typewriter, cooldown text) goes in frame().

Z-order. bringToFront() sets z-index to ctx.nextZ(), a counter that starts at 100, on open and on any pointerdown inside the window. HUD pieces use fixed small z-index values in ui.css (vignette 5, chat 14, minimap and buffs 15, Trial Hall panel 16, status bar 20, EXP bar 21, hotbar 22, banners 30–31), so any window is drawn above the HUD. The death prompt (50000), tooltip (60000) and drag ghost (70000) sit above windows.

Keeping windows above the HUD also means geometry. clampIntoView (window.ts:118) keeps at least 80 px of the window horizontally on screen while dragging, pushes it fully on screen when it opens, and keeps its bottom above HUD_TOP (720 − 66 = 654 px, the top of the status bar) minus 6 px whenever it re-renders or a drag ends, so a window that grows (a new tab, more dialog options) never slides under the hotbar.

Dragging a window uses pointer events on the title bar with setPointerCapture, converting through scaler.toLogical; the final position is saved to Layout. Dragging content (spells and potions to the hotbar, hotbar to hotbar) is a separate system, DragManager. drag.bind(el, () => payload) arms a source; a drag only starts after the pointer moves 5 px, so clicks and double-clicks still work. While dragging, a ghost icon follows the pointer, the slot under it gets ax-drop-hover, and hovering a hotbar page button dispatches a custom ax-drag-over event that flips the page. On release UIRoot.onDrop (UIRoot.ts:280) swaps or sets hotbar entries; dropping a hotbar entry onto the game world (not a window, hotbar or status bar) clears that slot. A capture-phase click listener eats the click that the browser fires at the end of a drag.

The HUD

hud.ts holds four always-on pieces.

  • StatusBar (hud.ts:60): level, name and "Year n · Job", HP and MP gauges, and the quick-menu buttons (Char, Items, Skills, Tasks, Help, Menu) whose key hints follow the bindings. A bag badge appears when the inventory is within 4 stacks of MAX_INVENTORY_STACKS, and a one-time banner fires when it is full. The full-width EXP bar is a separate element at the very bottom.
  • Gauge (hud.ts:20): each bar has a fill and a lag layer. The fill eases toward the target (rate dt/1000 × 14); the lag layer holds for 380 ms after a hit and then drains at least 25%/s, which draws the classic damage trail. Both are transform: scaleX(), so updates never trigger layout.
  • Hotbar (hud.ts:163): 24 entries in two pages of 12 (HOTBAR_SIZE, HOTBAR_PAGE_SIZE). Only 12 slot elements exist; each carries its absolute index (page × 12 + i) in data-hotbar-slot, rewritten on a page flip, so drops and swaps work across pages. Visual order mirrors the keyboard, two rows Q W E R T 1 / A S D F G 2 (HOTBAR_ORDER = [0, 1, 2, 3, 4, 10, 5, 6, 7, 8, 9, 11]). Page changes go through game.setHotbarPage(), and the bar follows the hotbar:page event. Right-click clears a slot.
  • BuffTray and Vignette: buff icons with a conic countdown ring that blink in their last 5 s and cancel on right-click; a red screen-edge vignette that fades in below 30% HP and pulses.

Cooldown overlays. Each frame, for every skill slot on the current page, the hotbar reads skills.getCooldownRemaining/Total and paints a conic-gradient wedge, only when the whole percentage changes. The text shows whole seconds above 1 s and tenths below. When a cooldown ends the slot plays an ax-ready blink; a slot whose MP cost exceeds current MP is dimmed.

Potion fallback. A potion slot keeps working after that potion runs out. The hotbar shows the item that useItem would actually drink, following the same strongest-first order:

  private displayedItem(id: string): string {
    const p = this.ctx.s.progression;
    if (p.countItem(id) > 0) return id;
    // Match useItem's strongest-first potion kinds; mixed HP/MP elixirs stay separate.
    const kinds = [['white_potion', 'orange_potion', 'red_potion'], ['mana_elixir', 'blue_potion']];
    return kinds.find(kind => kind.includes(id))
      ?.find(candidate => p.countItem(candidate) > 0 && Registry.item(candidate)?.consumable) ?? id;
  }

(hud.ts:270). The slot then shows the substitute's icon and count with an ax-potion-fallback marker, and its tooltip says "Out of Red Potion — using Orange Potion".

Dialogs, shops and the death prompt

dialogs.ts holds the three modal-ish surfaces. NPC scripts never touch them directly; they emit ui:dialog or ui:shop with a spec (see Story).

  • DialogWindow (dialogs.ts:15): portrait, name and title on the left; text typed at 70 characters per second on the right. The typed text sits over an invisible copy of the full text, so the box never resizes while typing. Click or Enter/Space skips; digits pick options. Each new spec increments gen, which lets choose() tell whether an option's action opened a follow-up dialog (then it must not close) or closed this one.
  • ShopWindow (dialogs.ts:111): Buy / Sell tabs with quantity steppers (−, +, +10). Selling equipment, or a stack worth 1,000 mesos or more, needs a second click ("Sure?"). Sell junk sells materials no unfinished assignment needs (another School's exam materials count as junk once you have declared) and unequipped gear at least 10 levels below you, again with a confirm that re-checks the list before selling.
  • DeathModal (dialogs.ts:286): "You have fallen…" with Return to Town, which calls progression.respawn(). UIRoot.update also shows it if the player is dead but ui:death was missed.

Banners, chat log, tooltip, minimap

  • Banners: an area banner near the top (map name or "Assignment Complete!", 2.8 s) and big centred banners (LEVEL UP!, EXAM PASSED) on a queue. An area banner that arrives while a big one is showing waits for it.
  • ChatLog: bottom-left system log, up to 60 lines, lines fade after 9 s.
  • Tooltip: one shared element. attach(el, build) builds the content lazily on hover, flips to the other side of the cursor near screen edges, hides during a drag, and check() hides it each frame if its anchor was removed by a re-render.
  • Minimap: a 2D canvas (at most 216×112, drawn at 2× resolution) with a static layer cached per map and player/NPC/monster dots refreshed about 12 times a second.
  • info.ts: shared tooltip builders (skillTooltip, itemTooltip), colours and names per School, and the derived-stat table.
Advanced: deduplicating logs and banners

Several systems announce the same moment, and the UI is where the repetition is removed. The rules, from the UI QA pass (c04ef65):

  • One owner per message. Progression logs "Level up!" and quest accept / ready / turn-in lines; UIRoot adds only banners. Before the QA pass both logged.
  • EXP is summed, not per kill. ui:log lines matching /^\+[\d,]+ EXP$/ are dropped; trackExp() diffs level/exp each frame (across level-ups, using expToNext) and feeds chat.gain('exp', …), which sums gains arriving within 2.6 s into one line.
  • Repeats collapse. ChatLog.push searches the last 6 lines for the same text within 5.2 s and turns it into "text (×n)", moving it to the bottom.
  • Talk-only story steps are silent. A step accepted and handed in within one conversation never shows "Ready to hand in", and "Assignment Complete!" waits 1 s (COMPLETE_DELAY_MS) and is cancelled if the quest was handed in meanwhile.
  • Banners collapse. Banners.enqueue updates a showing LEVEL UP! banner in place (with a bump animation) instead of queueing another, so arcana.levelTo(30) shows one banner. Several job advancements at once keep only the newest.

Title screen and Character Select

The Title screen is two layers. TitleScene.create() draws the backdrop in Phaser and plays the title music; TitleMenu builds the DOM menu in the same #ui-root with its own UIScaler.

The backdrop is composed from world art that BootScene already loaded: the sanctum sky, far mountains and mid ruins drifting as integer-scaled TileSprites, an additive tinted copy of the sky to lift it to moonlit indigo, a ×4 moon with a stepped halo, 90 twinkling pixel stars, shooting stars every 3.8 s, recoloured storm clouds and the mage tower (TitleScene.ts:119). Drift offsets are floored to whole source pixels every frame (Math.floor((t / 1000) * speed)) so nothing shimmers. If those textures are missing, the scene falls back to the procedural night sky in stepped colour bands and, on WebGL, adds Phaser's Pixelate post-FX.

The menu has four views: main (Continue, Character Select, New Game), select, new (name entry) and confirm (delete or replace). Character Select shows the six save slots (SAVE_SLOTS = 6) as cards in 3 columns with level, Year, job, map and play time; the selected card animates the student's idle cycle at 8 fps from frames read out of the player sheet with textures.getBase64. Keys: arrows choose, Enter plays, N new, Del delete, Esc back. Names must be 2–12 characters of letters, digits, space, - _ '. Starting a game calls markReturnToSelect(), so Quit to Title comes back to the slot just played. While the name field is focused, the menu disables Phaser's keyboard capture (titleMenu.ts:538). The file also starts loading both pixel fonts at import time, because Phaser name tags and damage digits rasterise text into canvases and need the real font before BootScene's document.fonts.ready resolves.

The graduation credits roll

creditsRoll.ts is armed when the graduation quest is first turned in and starts once no dialog, shop or death prompt is in the way. It is a full-screen overlay driven by frame(delta) from UIRoot.update, not CSS animations, so it follows the game loop: fade-in (1 s), title cards, then a roll that scrolls 52 px/s in whole 2 px steps. The art credits are not hard-coded: loadArtCredits() fetches each domain's CREDITS.md from public/assets (characters, monsters, world, vfx, vfx/holy, ui) and parseCreditsMarkdown reads every table with Author and License columns (creditsRoll.ts:79). It plays the title theme and restores the map's track afterwards, blocks gameplay input while open, and is remembered per save slot and character name so it plays once.

The rules the file follows (stated in its header):

  • Fonts. Kenney Pixel at 16 px is exactly one font pixel per CSS pixel; Kenney Mini is used at multiples of 8 px (16/24/32/48/64/96) for headings and banners. Bold and italic are forced off, and font smoothing is disabled.
  • Frames. Windows, the hotbar, minimap and title panel are 9-slice frames cut from Buch's CC0 "Golden UI", palette-swapped to indigo, drawn with border-image: var(--ax-img) 7 9 7 10 fill / 14px 18px 14px 20px, i.e. each source pixel at 2×. Buttons use the gold button images in normal, hover and pressed states; slots, wells, tooltips, tabs and gauge rims are hand-made 9-slices in the same palette.
  • Outlines. Text over the game uses --ax-outline, an 8-direction 2 px text-shadow that draws a hard pixel outline instead of a blur.
  • No smooth effects. No blurred shadows, rounded corners or smooth gradients: bevels are inset box-shadows, drop shadows have zero blur, and animations use steps().

uiIcons.ts turns icon specs and character looks into DOM elements. iconEl(spec, size) asks the art painter (iconDataUrl, see Art pipeline) for a data URL at twice the display size and renders an <img data-ik>; if there is no painter output it falls back to a CSS circle with the label's initial. Icons are drawn before the pixel icon sheet has loaded, so the module subscribes once to onPixelIconsReady and swaps the src of every live img.ax-icon[data-ik] when it arrives. portraitEl(look, size) does the same for dialog and exam portraits, with a CSS silhouette (robe, head, hat by hatStyle) as the fallback.

Advanced: subscriber leaks and destroy()

UIRoot is created once per GameScene run and destroyed on Quit to Title (GameScene's teardown calls s.ui.destroy()). Anything the UI registers outside its own elements outlives the elements unless it is removed, and a leaked closure keeps the whole old UI (and its services object) alive. The inventory of what destroy() (UIRoot.ts:384) undoes:

  • every bus subscription (unsubs) and pending "Assignment Complete" timers;
  • the window keydown listener and the root's contextmenu / dragstart / mousedown listeners;
  • Phaser's keyboard capture, re-enabled if the UI was blocking input when torn down;
  • each component's own: the status bar's onPixelIconsReady and onBindingsChanged unsubscribers, the hotbar's hotbar:page subscription, the quests window's bindings listener, the menu's settings listener and the Controls window instance, banner timers, the drag manager's capture-phase click listener, the scaler's resize listeners and ResizeObserver.

onPixelIconsReady returning an unsubscribe function is itself a fix from the final pixel QA (67893fe, "icon subscriber leak"): the status bar used to register a callback per UIRoot that was never released. When you add a component, give it a destroy(), call it from UIRoot's destroy(), and route every bus.on / onXxxChanged through something that remembers the unsubscriber. GameScene's teardown (on scene SHUTDOWN) calls bus.removeAll() after ui.destroy(), which is a backstop for bus listeners only: window/document listeners, the icon-sheet callbacks and the bindings and settings listeners live outside the bus and are released only by destroy(). Two more edges: the uiIcons module-level subscription and caches are intentionally global (shared by Title and Game), and destroy() is idempotent (destroyed flag), so a second call is harmless.

Advanced: keyboard focus, F5 and other browser defaults
  • Rebindable keys can collide with browser shortcuts. If a player binds the Spellbook to F5, the browser would reload the page. keyDown calls preventDefault() for any key bound to a UI action, before the e.repeat check, so even auto-repeat never reaches the browser (UIRoot.ts:261). Gameplay keys get the same treatment from Phaser's global key capture, which is why blocking input must disable that capture.
  • Buttons never take focus. A root-level mousedown handler calls preventDefault() on buttons. Otherwise a clicked button keeps focus and the next Space (jump) or Enter clicks it again. The title menu does the same for buttons and save cards, and settings sliders blur themselves on release.
  • Synthetic keys. The gamepad bridge dispatches keyboard events on window. Those reach listeners in registration order rather than capture-phase first, which is why UIRoot explicitly asks controlsClaimKey(e) before acting (controlsWindow.ts:222).
  • Right-click and native drag are disabled on the overlay (contextmenu, dragstart), because right-click means "clear slot" or "cancel buff" here.
Advanced: why DOM instead of Phaser UI, and what it costs

The architecture fixes the split (DOM for windows and HUD, Phaser for damage numbers and name tags); these are the trade-offs it buys.

  • Gains. Text layout, wrapping and scrolling lists (the Spellbook holds up to 24 spells per School), real <input> elements for names and sliders, hover and right-click events per element, 9-slice frames through border-image, and windows that stay crisp at any canvas scale because the browser re-rasterises text after the CSS scale(). None of it touches the WebGL renderer, so a busy Spellbook costs no draw calls.
  • Costs. Two coordinate systems (client pixels vs. logical pixels: always go through toLogical); DOM writes are expensive enough that the HUD caches every value it writes (setText, toggleClass, lastCd, signatures); and the overlay cannot sit between world layers, so anything that must be occluded by sprites has to be a Phaser object.
  • Failure modes. The UI must survive missing services and data: calls into other systems are wrapped in safe(), render errors are caught per window, and a failed icon or portrait falls back to CSS. The z-index counter never resets during a session; it would need about 50,000 window raises to pass the death prompt's 50000, so in practice windows stay below it.
