Build, deploy and these docs

The Academy ships as a folder of static files. There is no server code: Vite bundles the TypeScript into JavaScript chunks, copies public/ (the pixel-art PNGs and fonts) next to them, and the result runs from any static host. One build produces three pages that share code: the game (index.html), the Student Handbook (guide.html) and this page (devdocs.html). This section walks through the build configuration, the GitHub Pages workflow, the one-file Artifact build used before the repository was public, and how the developer docs themselves are put together.

Scripts

Everything goes through the four scripts in package.json:

  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build",
    "typecheck": "tsc --noEmit",
    "preview": "vite preview"
  },
  • npm run dev starts the dev server on port 5199 (set in vite.config.ts). Vite serves each module on demand, so the first load of the game requests a few hundred files; edits hot-reload.
  • npm run build typechecks first. Vite itself only strips types (it uses esbuild), so without tsc --noEmit a type error would happily ship. A failing typecheck stops the deploy.
  • npm run preview serves dist/ exactly as a static host would, which is the only way to test the relative base and the chunk split locally.

The only runtime dependency is phaser; typescript and vite are dev dependencies. Audio is synthesized (Synthesized audio) and all art is PNG under public/assets/ (Art pipeline), so there are no loaders or plugins for media.

vite.config.ts

The whole configuration, minus the developer-docs plugin described below (vite.config.ts:51):

export default defineConfig({
  base: './',
  server: { port: 5199 },
  plugins: [devdocsSource()],
  build: {
    chunkSizeWarningLimit: 4000,
    rollupOptions: {
      input: {
        main: resolve(__dirname, 'index.html'),
        guide: resolve(__dirname, 'guide.html'),
        devdocs: resolve(__dirname, 'devdocs.html'),
      },
      // Phaser rarely changes between releases; a separate chunk keeps it cached across game updates.
      output: { manualChunks: { phaser: ['phaser'] } },
    },
  },
});
SettingWhy
base: './'Every URL Vite writes into the HTML is relative, so dist/ works at https://minormending.github.io/the-academy/, at a domain root, or opened from any folder. Added in the commit "Build: relative base so the static build runs from any path".
input (three pages)A multi-page build: each HTML file is an entry, and modules they share (the data files, the Registry, Phaser) become shared chunks instead of being duplicated.
manualChunks: { phaser }Phaser is about 1.2 MB minified. In its own file (assets/phaser-<hash>.js) its hash only changes when Phaser is upgraded, so returning players re-download only the game's own code after an update.
chunkSizeWarningLimit: 4000Silences Vite's 500 kB warning: the Phaser chunk is big by nature and splitting it further would not help.

Runtime asset paths follow the same rule. The art manifests never hard-code /assets/…; they go through assetUrl(), which prefixes Vite's BASE_URL: 

export function assetUrl(path: string): string {
  return `${import.meta.env.BASE_URL}assets/${path}`;
}

CSS is different: url("/assets/ui/fonts/KenneyPixel.ttf") in a stylesheet is rewritten by Vite at build time to a path relative to the emitted CSS file, so root-relative URLs are fine there.

Files under public/ are copied verbatim (no hashing), which is why the art manifests can name them by path. Everything imported from TypeScript gets a content hash in its file name, so a static host can cache it forever.

Advanced: why the docs page loads Phaser for some charts

The spell definitions in src/skills/*.ts import playVfx from src/core/vfx.ts, which imports Phaser, and the Registry imports every skill. So any page that needs the spell list pulls in Phaser, even though it never creates a Phaser.Game. Importing Phaser has no side effects beyond defining the library, so this is safe, only heavy. The developer docs therefore import the pure data modules (balance, maps, monsters, jobs, items, quests) statically and load skills, derived stats and saves with a dynamic import() in charts/index.ts:54, only when a spell chart scrolls near or the page is idle. The chunk is the same phaser-<hash>.js the game uses, so a reader who has played is served it from cache.

Splitting the VFX imports out of the skill definitions would make the spell data Phaser-free, but it would mean editing all six School files and the contract that VFX keys are strings resolved at cast time already provides most of the decoupling. It was not worth it for a documentation page.

GitHub Pages workflow

Every push to main runs the tests, typechecks, builds and deploys all three pages (.github/workflows/pages.yml). It is the standard two-job Pages workflow: build tests and bundles the game, then uploads dist/ as a Pages artifact, and deploy publishes it. A failing test stops the deploy, so the live site is always a commit that passed (see Unit tests). 

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

# One run at a time: a newer push cancels any queued or running one, so only the newest commit deploys.
concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - name: Test
        run: |
          npm run typecheck:tests
          npm test
      - name: Typecheck and bundle
        run: npm run build
      - uses: actions/configure-pages@v6
      - uses: actions/upload-pages-artifact@v5
        with:
          path: dist
  # … deploy: needs build, runs actions/deploy-pages@v5
  • Least privilege: the token can read the repo and write Pages; id-token: write is what deploy-pages uses to prove the artifact came from this workflow.
  • npm ci installs exactly package-lock.json, so CI builds what was tested locally.
  • cancel-in-progress: two quick pushes never race to deploy an older build last.
  • The repository's Pages source must be set to GitHub Actions (a one-time setting) for deploy-pages to publish.

Node 22 in CI also runs vite.config.ts, which imports src/devdocs/check.mjs and through it two .ts files. That file is bundled by Vite's config loader (esbuild), so it does not depend on Node's own TypeScript support. Running node src/devdocs/check.mjs by hand does: it needs Node 22.6 or newer.

Unit tests

npm test runs a Vitest suite from tests/, and npm run typecheck:tests typechecks it with tsconfig.test.json (the ordinary tsc --noEmit only covers src/). The tests are not about Phaser rendering. They check that the data the game and these docs are built from hangs together, so a bad edit is caught before anyone plays it:

  • skills: every skill's id, job, prerequisites, attack spec and numbers at every level. vfx: every VFX key a spell names is registered (an unregistered key does not crash, it silently plays a white puff).
  • world: every id that monsters, items, quests, maps, NPCs and shops point at exists. graduation: every School can be finished, and its exam items drop somewhere reachable.
  • balance, stats, save, bindings and keytext: the reference curves, the derived-stat formula, save repair and round trips, key rebinding, and the {key:action} placeholders in player-facing text.

Phaser touches window when it is imported, so Node cannot load it. Vitest aliases every import 'phaser' to a small stub (phaser-stub.ts): the event emitter is real and everything else is an inert proxy, which is just enough for the data, the VFX registration and the pure systems to load. Anything that needs a real scene belongs in the browser, not here.

Advanced: what the tests do not cover

The stub makes the suite fast and dependency-free, but it also means a spell's onCast body, the lifetime helpers described in Phase 9 and anything else that needs a live scene is only checked by playing the game. The data sweeps are the safety net for content; the physics and the cast flow still need the browser. The handbook's own validator (src/guide/validate.ts) and the docs checker (node src/devdocs/check.mjs) run separately and are not part of the Vitest run.

The one-file Artifact build

Before the repository went public, the playable build was shared as a private Artifact page. The host of such a page supplies the document skeleton, so scripts/make-publish-page.mjs reads the built dist/index.html, keeps only its <script> and <link> tags, and wraps them with the game's stage markup into dist/academy.html: 

const html = readFileSync('dist/index.html', 'utf8');
const tags = [...html.matchAll(/<(script|link)[^>]*>(<\/script>)?/g)].map(m => m[0]).join('\n');
const page = `<title>The Academy</title>
// …
${tags}
<div id="stage">
  <div id="game"></div>
  <div id="ui-root"></div>
</div>
`;
writeFileSync('dist/academy.html', page);

It works only because of base: './': the script tags point at ./assets/…, which resolve next to the page wherever dist/ is uploaded. ROADMAP.md records the republish command: npm run build && node scripts/make-publish-page.mjs.

How these developer docs are built

This page follows the same design as the developer docs of the sister project Verdant Reach: writers supply HTML fragments, one per section, and a page shell turns them into the page. The full write-up is docs/DEVDOCS.md; the rules for writers are in src/devdocs/CONTRACT.md.

  • Fragments live in src/devdocs/sections/ and are bundled as raw strings. The shell parses them with a <template>, numbers the headings, and builds the contents and search index from what it finds (main.ts:476).
  • Source links are plain <a data-src="src/core/balance.ts#L7">; the shell turns them into GitHub links on main (enhance()).
  • Diagrams are Mermaid source in <pre class="mermaid">. Mermaid is not an npm dependency: mermaid.ts imports a pinned ESM build from jsDelivr at runtime, on this page only, when the first diagram nears the viewport. If the CDN is unreachable each diagram shows its source instead.
  • Charts are <figure data-chart="NAME">. Their numbers are computed in the browser from the game's own modules (expToNext, MONSTERS, ALL_SKILLS, computeDerived…) and drawn as plain SVG with tooltips and a "Show data" table, so they cannot drift from the build.

Some charts need facts about the source tree that the browser cannot see: the module-graph in Architecture and the line counts in the overview. A small Vite plugin computes them at build time.

That plugin, devdocsSource (vite.config.ts:20), serves two virtual modules: modules with no file on disk whose code the plugin generates. Only devdocs.html imports them, so the game bundle never contains them. 

    load(id) {
      if (id === `\0${SOURCE}`) {
        const files = Object.entries(repoFiles(root))
          .filter(([p]) => p.startsWith('src/') && p.endsWith('.ts'))
          .map(([path, text]) => ({ path, text }));
        return `export default ${JSON.stringify(sourceStats(files))};`;
      }
      if (id === `\0${FILES}`) {
        const lines = Object.fromEntries(Object.entries(repoFiles(root)).map(([p, t]) => [p, lineCount(t)]));
        return `export default ${JSON.stringify(lines)};`;
      }
      return undefined;
    },
  • virtual:devdocs-source: lines and files per src/ folder and the import statements between folders (a few hundred bytes of JSON instead of the 44,000 lines of source).
  • virtual:devdocs-files: the line count of every text file in the repository, imported only in dev so the page can check that every data-src path exists and its #L line is in range.

The same fragment checks run three ways:

node src/devdocs/check.mjs          # lists every problem, exits 1 if there are any
npm run build                       # prints them as warnings
DEVDOCS_STRICT=1 npm run build      # fails the build on them
Advanced: what the checker catches and what it cannot

validate.ts is pure string scanning with no DOM and no imports, so the browser, Node and the Vite plugin all run the same code. It rejects anything outside a small allow-list of elements (an unknown element is almost always an unescaped < in a code sample, such as Map<string, T>), scripts, styles, inline handlers, images, duplicate or unprefixed ids, unknown chart names and code languages, #links to ids that do not exist, and source links to missing files or past the end of a file.

It cannot tell whether #L120 still points at the function the text describes. Line links drift when code above them changes. The checker guarantees the link resolves; keeping it right is a review job: after a refactor, grep the sections for the file name and re-check the numbers with grep -n.

Problems are warnings in a normal build on purpose: a stale docs link should not block a game fix from deploying. CI could opt into DEVDOCS_STRICT=1 once the docs are part of the review routine.
