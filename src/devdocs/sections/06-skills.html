Skill engine, combat and statuses

Every spell in The Academy is data: a SkillDef object in one of the six spell files (apprentice.ts, fire.ts, ice.ts, lightning.ts, holy.ts, shadow.ts). There are 130 of them: 10 Year-1 Apprentice spells and 24 per School. A small skill engine turns that data into gameplay. It has three parts:

  • SkillSystem.ts decides whether a cast happens (learned, MP, cooldown, busy) and owns everything that lasts: cooldowns, buffs, summons and movement.
  • AttackRunner.ts runs one AttackSpec: it finds the targets for one of seven attack patterns, simulates projectiles and schedules the damage lines.
  • CombatSystem.ts does the arithmetic: it rolls damage, applies it to monsters, applies status effects, works out damage the player takes, and shows the floating numbers through DamageNumbers.ts.

The spell files never touch Phaser physics, monsters or HP directly. They describe what a spell does (pattern, damage %, hit lines, area, status, VFX keys) and the engine decides how. Content agents built the five Schools in parallel against this contract, which ARCHITECTURE.md calls "Skill engine semantics". This section walks through the contract, follows one cast from key press to damage number, and then covers the combat math and statuses that the patterns feed into.

The SkillDef contract

All skill types live in src/core/types.ts (see Architecture for why contracts live there). A skill has one of five kinds: attack, buff, passive, movement and summon. Each kind has its own optional field holding its spec.

export interface SkillDef {
  id: string;               // prefix: app_ / fire_ / ice_ / ltn_
  name: string;
  description: string;      // one line; may mention {dmg} etc. — UI shows plain text
  element: Element;
  job: JobId;               // job that teaches it (tier implied by job)
  kind: SkillKind;
  maxLevel: number;
  icon: IconSpec;
  requires?: { skillId: string; level: number }[];
  mpCost: (lv: number) => number;
  cooldownMs?: (lv: number) => number;
  castTimeMs?: number;      // player animation lock (default 450)
  attack?: AttackSpec;      // kind 'attack'
  buff?: BuffSpec;          // kind 'buff'
  passive?: (lv: number) => StatModifier[]; // kind 'passive' (always on while learned)
  movement?: MovementSpec;  // kind 'movement'
  summon?: SummonSpec;      // kind 'summon'
  sfx?: SfxKey;
  /** Escape hatch: replaces the default behaviour entirely. Use sparingly. */
  onCast?: (ctx: SkillContext, lv: number) => void;
}

Source: types.ts:190. Holy (holy_) and Shadow (shd_) were added in Phase 3; the id comment predates them.

Anything that changes with skill level is a level function, (lv) => number, and not a table. Each School file defines its own small helpers for these. Fire uses L(a, b, max), a linear ramp from a at level 1 to b at max, plus Li (the same, rounded) and K(n) (a constant). Apprentice uses an inline lerp. This keeps a spell readable at a glance, because damagePct: L(170, 262, 20) says "170% at level 1, 262% at level 20". The engine also never needs to know how many levels a spell has. It clamps the learned level to maxLevel before it calls anything.

AttackSpec

Attacks carry most of the data. One AttackSpec describes a whole cast: the pattern (the shape that decides which monsters are hit), damage per hit line as a % of magic attack (matk), how many lines each target takes, how many targets at most, and the optional status, bonus and VFX keys.

export interface AttackSpec {
  pattern: AttackPattern;
  damagePct: (lv: number) => number;   // % of matk per hit (see balance.ts for reference ranges)
  hits: (lv: number) => number;        // damage lines per target (Maple-style multi-hit)
  maxTargets: (lv: number) => number;
  range: number;                       // px forward reach (projectile max travel, aoe_target search, beam length)
  area?: { w: number; h: number; offsetX?: number; offsetY?: number }; // for melee_arc/aoe_self/aoe_target/beam/rain/projectile-explosion
  projectile?: {
    speed: number;          // px/s
    radius: number;         // collision radius
    pierce?: boolean;       // keep going through targets (up to maxTargets)
    gravity?: number;       // px/s^2 (arcing projectiles); default 0
    explodeArea?: { w: number; h: number }; // on first impact deal damage to all in area (up to maxTargets)
    count?: (lv: number) => number;  // number of projectiles fired (fanned / staggered)
    spreadDeg?: number;     // fan spread between projectiles
  };
  chain?: { jumpRange: number; jumpDelayMs?: number };
  rain?: { count: (lv: number) => number; spreadX: number; intervalMs: number; fallHeight?: number };
  status?: StatusSpec;
  /** Bonus damage vs. targets that have a status, e.g. shatter frozen. */
  bonusVs?: { status: StatusKind; mult: number; consume?: boolean };
  knockback?: number;       // px pushed away from caster
  delayMs?: number;         // delay from cast start to first damage (sync with vfx)
  hitIntervalMs?: number;   // delay between multi-hit lines (default 90)
  vfx: {
    cast?: string;          // played at caster on cast
    projectile?: string;    // visual that travels with a projectile (engine owns lifetime)
    hit?: string;           // played on each damaged target
    area?: string;          // played at the area / impact point
  };
}

The other three specs are small. Summons reuse AttackSpec for their own attack, so a summon is "an attack that repeats from somewhere else".

export interface BuffSpec {

export interface MovementSpec {
  kind: 'blink';            // instant teleport in input direction (left/right/up/down), default facing
  distance: (lv: number) => number;
  vfxOut?: string;          // at origin
  vfxIn?: string;           // at destination
}

export interface SummonSpec {
  durationMs: (lv: number) => number;
  attackIntervalMs: number;
  attack: AttackSpec;       // executed from the summon's position, facing nearest monster
  vfx: string;              // persistent body visual (engine owns lifetime); positioned at summon x/y
  offset: { x: number; y: number }; // spawn offset relative to caster (x mirrored by facing)
  follow?: boolean;         // hovers near the player if true, else stationary
}

export function castHeal(ctx: SkillContext, pct: number, matkShare: number, attack: AttackSpec): void {
  const p = ctx.services.player;
  const d = ctx.services.progression.derived();
  playVfx(ctx.scene, 'holy_heal_self', { x: p.x, y: p.y, facing: p.facing, lv: ctx.level });

  ctx.runAttack(attack, bodyOrigin(ctx));
}

The cast flow

GameScene calls skills.tryCast(id) every frame a hotbar key is held, so holding a key repeats the spell as fast as the cast lock allows. The cast buffer, the hold-to-repeat rule and the hotbar pages are covered in Input. tryCast makes its checks in a fixed order and stops at the first one that fails:

  tryCast(skillId: string): CastResult {
    const def = Registry.skill(skillId);
    if (!def) return 'unknown';
    const s = this.services;
    const learned = s.progression.state.skills[skillId] ?? 0;
    if (!(learned > 0)) return 'not_learned';
    if (def.kind === 'passive') return 'passive';
    if (s.progression.isDead() || s.player.state === 'dead') return 'dead';
    if (s.player.isBusy()) return 'busy';
    if ((this.cooldowns.get(skillId)?.remaining ?? 0) > 0) return 'cooldown';
    const lv = Math.max(1, Math.min(learned, def.maxLevel || learned));
    const cost = Math.max(0, Math.round(num(def.mpCost(lv), 0)));
    if (!s.progression.spendMp(cost)) return 'no_mp';

    const d = s.progression.derived();
    if (def.cooldownMs) {
      const cd = num(def.cooldownMs(lv), 0) * (1 - clamp(num(d.cdr, 0), 0, 0.8));
      if (cd > 0) this.cooldowns.set(skillId, { remaining: cd, total: cd });
    }
    const baseCast = def.castTimeMs ?? (def.kind === 'movement' ? 150 : 450);
    const lock = Math.max(0, Math.round(baseCast * (1 - clamp(num(d.castSpeed, 0), 0, 0.75))));
    safe(() => s.player.playCast(lock));
    if (def.sfx) safe(() => s.audio.play(def.sfx!));
    bus.emit('skill:cast', { skillId });
    safe(() => this.execute(def, lv));
    return 'ok';
  }

Source: SkillSystem.ts:54

  • Busy means the player is dead, on a rope or ladder, in a cast lock, or in hit-stun (Player.ts:185). You cannot cast while climbing.
  • Cooldown is reduced by the derived stat cdr, capped at 80%. It starts the moment the cast succeeds, not when the effect ends.
  • Cast lock is how long the player is frozen in the cast pose: castTimeMs (default 450 ms, or 150 ms for movement skills) reduced by castSpeed, capped at 75%. player.playCast(lock) extends the lock, never shortens it, and stops horizontal movement only when grounded, so a mid-air cast keeps its momentum (Player.ts:244).
  • MP is spent through progression.spendMp, which returns false (and spends nothing) if the player has too little.
  • skill:cast on the event bus is emitted before the spell runs. Today its only listener is the HUD, which flashes the hotbar slot (UIRoot).

execute then dispatches. If there is an onCast it runs that and nothing else. Otherwise it picks by kind: attacks go to AttackRunner.run from the cast point, buffs to startBuff, movement to doMovement, summons to spawnSummon. The cast point is the tip of the staff: x = player.x + 18·facing, y = player.y − 34, where player.y is the feet (CAST_OFFSET, SkillSystem.ts:13). The origin also carries groundY (the player's feet) and centerX (the body, not the staff), which rain and aoe_self use.

All timing inside the engine goes through a small Scheduler (util.ts:23). It is driven by SkillSystem.update(dt) and does not use Phaser's scene timers. after(ms, fn) with ms <= 0 runs immediately. clear() drops everything pending, which is how a map change or the player's death cancels hit lines, chain jumps and rain impacts that have not landed yet.
Advanced: order-of-operations invariants in tryCast
  • Pay before you act. MP is spent and the cooldown started before execute. execute is wrapped in safe(), so a spell that throws still returns 'ok' and the MP is gone. The error is logged as [skills]. This trade-off is deliberate: a broken spell must never crash the frame loop (ARCHITECTURE rule 8, "never throw in update").
  • The level is clamped once, to 1..maxLevel. Every level function receives a value in range, even for a save that holds a level above the current maxLevel after a rebalance.
  • Checks are cheap first, then stateful. Nothing changes state until spendMp succeeds, so a 'busy' or 'cooldown' result is free. GameScene relies on this, because it calls tryCast every frame a key is held.
  • Derived stats are read after paying MP. cdr and castSpeed come from progression.derived(). A buff that raises cast speed applies to the very next cast after it starts, because startBuff invalidates the derived-stats cache.
  • Every num() is a guard. Level functions written by other agents could return NaN. num(v, fallback) replaces any non-finite value, so a bad spell degrades to a default and never poisons HP with NaN.

The seven attack patterns

AttackRunner.run plays vfx.cast at the origin, then switches on the pattern (AttackRunner.ts:73). An unknown pattern logs a warning and does nothing. Every pattern ends in the same place: strike(info, monster, fromX), which deals all the hit lines to one target. They differ only in where the area is and which monsters fall inside it.

"In front" always means the same helper, frontNearest (AttackRunner.ts:145). It looks for a living monster on the facing side (a monster overlapping the caster counts), within range measured to its near edge, and within 140 px vertically (FRONT_MAX_DY). It ranks them by |dx| + 0.6·|dy|, so a foe at the same height wins over a slightly closer one on another platform. The area patterns gather targets with inRect, which sorts by distance from a reference point and keeps the first maxTargets.

Projectiles in detail

  • Count and fan. projectile.count(lv) shots are fired. With spreadDeg they leave together in a fan, (i − (count−1)/2) × spreadDeg degrees apart. Without it they are staggered 70 ms apart with a small ±6 px vertical jitter, like a burst.
  • Fans share one hit set, so each shot in a volley strikes a different foe (Ember Volley: "each strike a different foe"). Without this a five-dart fan would put all five darts into the nearest monster.
  • Gravity and auto-lob. With gravity > 0 the engine adds an upward velocity of gravity·T/2, where T = range / |vx|, so the arc comes back down to launch height at range. The kill distance becomes range × 1.6, measured horizontally. Arcing shots also land on one-way platform tops (Firebomb bursts on "the first enemy or surface it touches").
  • Sub-stepping. Each frame is split into ceil(speed·dt / max(8, radius)) steps so fast needles (Galvanic Needle flies at 1,050 px/s) cannot tunnel through a small monster. The vertical hit test is lenient (max(radius, 18)) so straight shots still hit short slimes.
  • Walls (map solids) kill the shot, or detonate it if it has explodeArea. Leaving the map or passing range also kills it.
  • Aimed shots. Summons pass aimAt. Their shots head for the target's centre, with the angle clamped to ±60°.

Chain and rain

A chain waits delayMs, picks frontNearest, plays vfx.area as a segment from the origin to the target, strikes, then after jumpDelayMs hops to the nearest unvisited monster within jumpRange of the last target's centre. If nothing is in front it fizzles: it draws a short segment 45% of range long so the button press still reads on screen.

A rain snaps its zone onto the nearest monster in front, unless the author pinned it with area.offsetX. Then it spaces count x positions evenly over spreadX, jitters each one slightly, shuffles them (so impacts don't sweep left to right) and drops one every intervalMs from fallHeight above the ground. Falling bodies are projectiles with a faller flag. They ignore monsters mid-air and only resolve on landing, at the walkable surface groundY.

Hit lines, delays and stacked numbers

MapleStory-style multi-hit is the heart of the engine. hits(lv) is the number of separate damage lines each target takes from one strike. Each line is rolled on its own and shown as its own number, stacked upward.

  strike(info: CastInfo, m: IMonster, fromX: number, playHit = true): void {
    const spec = info.spec;
    const s = this.svc();
    const lines = Math.max(1, Math.round(num(spec.hits(info.lv), 1)));
    const interval = Math.max(0, num(spec.hitIntervalMs, 90));
    const base = info.stacks.get(m.uid) ?? 0;
    info.stacks.set(m.uid, base + lines);

    let pct = num(spec.damagePct(info.lv), 100);
    let consume = false;
    if (spec.bonusVs && m.hasStatus(spec.bonusVs.status)) {
      pct *= num(spec.bonusVs.mult, 1);
      consume = !!spec.bonusVs.consume;
    }
    if (playHit && this.allowHitVfx(spec.vfx.hit)) {
      // … play vfx.hit once at the target centre
    }
    for (let i = 0; i < lines; i++) {
      this.sched.after(i * interval, () => {
        if (!m.alive) return;
        const r = s.combat.rollSkillDamage(info.element, pct, m);
        s.combat.damageMonster(m, r.amount, {
          crit: r.crit, element: info.element, fromX,
          knockback: i === 0 ? spec.knockback : undefined,
          stackIndex: base + i,
        });
        if (i === 0) {
          if (consume && spec.bonusVs) safe(() => m.removeStatus(spec.bonusVs!.status));
          if (spec.status && m.alive) s.combat.tryApplyStatus(m, spec.status, info.lv, info.element, r.amount);
        }
      });
    }
  }

Source: AttackRunner.ts:193

  • delayMs delays the first damage from the cast so it lines up with the VFX (Meteor Storm waits 600 ms, Supernova 650 ms). The area VFX plays at once and the damage lands later.
  • hitIntervalMs (default 90 ms) spaces the lines. Plague Cloud uses 500 ms, so its three lines read as a lingering cloud.
  • Knockback is applied by line 0 only, so a 3-line spell does not shove three times.
  • CastInfo.stacks is one map per cast. When a target is struck again by the same cast (a second rain impact, an explosion after a pierce), its new lines carry on stacking above the earlier ones instead of drawing on top of them.

DamageNumbers.ts draws the numbers from per-kind glyph atlases built from the CC0 "Kenney Pixel" font (monster, crit, player, heal, mp, miss, dot; DamageNumbers.ts:28). show lifts each number by (stackIndex % 12) × 26 px times the size setting (DamageNumbers.ts:243). The objects are pooled, and when more than 90 are alive the oldest is recycled (MAX_ACTIVE, DamageNumbers.ts:41).

Advanced: why roll every line separately, and the review fixes
  • Per-line rolls are a feel decision from MapleStory. Every line gets its own rand(mastery..1) roll and its own crit chance, so a 3-line spell shows three different numbers and sometimes one pink crit. The expected total equals one big roll, but the spread is narrower, so multi-hit spells feel more reliable. The roll happens when the line lands, not when the spell is cast, so a shock applied by line 1 (or by another spell in between) raises lines 2 and 3.
  • bonusVs is decided once per strike, before any line lands, so all lines of Combust (burn ×2.4, consumed) get the bonus even though line 0 removes the burn. A second strike from the same cast (another rain impact) no longer sees the status.
  • The status uses line 0's actual damage as its base. Burn and poison potency is "% of the hit". The hit passed in is r.amount, already through crit, weakness, shock and the monster's flat def. A crit on the first line therefore means a stronger burn.
  • Fan volleys spread across distinct foes (the "Codex review fixes" commit). A fan advertises "N targets × damage", not "N × damage on one target", so runProjectile gives every shot of a fanned volley one shared hitSet (AttackRunner.ts:375). Staggered bursts (a count with no spreadDeg) keep one hit set per shot, so every shot may hit the same target. No current spell uses that mode: Ember Volley, Glacial Lance and Prism all fan.
  • Fields wake on their rectangle. The same commit fixed stationary aoe_self summons such as Wall of Fire. They only attacked when a monster was within w/2 of their centre, a circle smaller than their rectangle. Now the wake-up reach is the rectangle's half-diagonal, hypot(w/2, h/2), and the vertical tolerance is max(160, h/2 + 20) (SkillSystem.ts:220).

VFX conventions

Spells name their visuals by string key. The keys resolve through a global registry in src/core/vfx.ts. A VFX function receives the scene and a VfxOptions (position, facing, optional target point, area size, level, projectile angle and groundY, the walkable surface under the effect). It draws something.

export function registerVfx(key: string, fn: VfxFn): void {
  if (registry.has(key)) console.warn(`[vfx] duplicate key ${key} (overwriting)`);
  registry.set(key, fn);
}

export function hasVfx(key: string): boolean { return registry.has(key); }

/** Play a VFX. Missing keys fall back to a generic puff so nothing crashes. */
export function playVfx(scene: Phaser.Scene, key: string | undefined, o: VfxOptions): Phaser.GameObjects.GameObject | void {
  if (!key) return;
  const fn = registry.get(key);
  if (fn) return fn(scene, o);
  if (!warned.has(key)) { warned.add(key); console.warn(`[vfx] missing key "${key}"`); }
  const c = scene.add.circle(o.x, o.y, 10, 0xffffff, 0.8).setDepth(DEPTH.VFX);
  scene.tweens.add({ targets: c, scale: 2.5, alpha: 0, duration: 250, onComplete: () => c.destroy() });
}

Advanced: the hit-VFX throttle

A Year-4 ultimate can strike 12–15 monsters with 3–4 lines each, and a rain hits on every impact. Buffs, passives, summons and movement

Buffs

A buff is a timed set of StatModifiers ({ stat, add?, mul? }). Progression combines all modifiers as final = (base + Σadd) × (1 + Σmul) (see Progression). startBuff stores the modifiers for the cast level, plays buff.vfx at the feet, creates the aura, and calls buffsChanged(). That calls progression.invalidate() and emits player:changed, which the UI uses to redraw the buff bar and stats.

  • Recasting refreshes an active buff: the duration resets to the new total and the modifiers are recomputed. The aura is kept if it is still alive. Buffs do not stack with themselves.
  • Expiry runs endBuff, which fades the aura over 200 ms, deletes the buff and invalidates again. cancelBuff(id) calls the same function, for UI or scripted removal.
  • Map changes keep buffs. clearWorld() destroys the auras (they belong to the old scene objects) and marks them needsAura, and the next update rebuilds them on the new map.
  • Death clears all buffs and summons (onPlayerDied).

Derived stats are cached, so the cache must be cleared whenever a modifier source changes. The engine pushes buff modifiers through getBuffModifiers(), which Progression reads while recomputing (Progression.ts:68). That is why every buff start and end has to call invalidate().

Passives

The engine does almost nothing for passives: tryCast answers 'passive' and that is all. Progression's persistentModifiers walks every learned skill with a passive function and adds its modifiers next to the equipment modifiers (stats.ts:49). Passives have no cast event, so a few Schools make them visible by checking for them inside another spell's onCast. Lightning's studiedAttack plays a Live Wire or Perfect Conductor sigil on the cast if those passives are learned (lightning.ts:23).

Summons

Only one copy of each summon exists at a time. Recasting destroys the old one first. Different summons do coexist, so a Necromancer can have a skeleton and a wraith out together. spawnSummon places the body at player + offset (with x mirrored by facing) and arms the first attack after min(400, attackIntervalMs), so a fresh summon acts almost at once. Each frame updateSummon:

  1. counts down the lifetime and destroys the summon with a 250 ms fade at zero;
  2. if follow is set, moves it toward player + offset with frame-rate-independent easing (k = 1 − e^(−6·dt), so about 6 per second) and copies the player's facing unless it has just attacked. Stationary summons (follow: false, such as Wall of Fire and Raise Skeleton) stay where they were cast;
  3. when the attack timer fires (no faster than every 100 ms), finds the nearest monster in any direction (nearestAny), turns to face it (and holds that facing for 600 ms), and runs its AttackSpec from its own position with aimAt set to the target's centre.
      const atk = spec.attack;

If no monster is in reach the summon skips that tick and tries again one interval later. Summon damage goes through the same strike and the same combat math as the player's own spells, using the player's current matk.

Movement

doMovement reads the held direction from player.getAimDir(): horizontal wins, then vertical, and with nothing held the player blinks forward. It plays vfxOut at the old feet, calls player.blink(dx, dy) and plays vfxIn at wherever the player actually ended up. The player keeps the blink inside the map and stops it at the last spot that does not overlap a solid, as covered in Physics. Fancier movement spells (Flame Dash, Holy Step, Flash Relay) use onCast to copy this logic and then add damage or healing along the path.

onCast: heals, drains and fields

onCast(ctx, lv) receives a SkillContext: the scene, all services, the def, the level, and runAttack(spec, origin) (SkillSystem.ts:87). runAttack is the same AttackRunner.run the engine uses, with groundY set to the player's feet and centerX set to origin.x. Custom spells therefore get every pattern, stacked numbers, statuses and VFX conventions for free, and only write the part that is really custom:

  • Heals call progression.heal(hp, mp), measure what actually landed (HP is capped at max) and show it with combat.showNumber(x, y, amount, 'heal'). Holy's restore() helper does both.
  • Drains (Soul Drain) run an attack and heal a % of max HP on cast.
  • Costs in HP (Immolation) take up to 6% of max HP but never the last point, then attack.
  • Fields (Consecration) run an aoe_self every 800 ms from a fixed point (holy/casts.ts:78).

For an aoe_self centred on the mage, pass the body as the origin ({ x: p.x, y: p.y − 34 }, Holy's bodyOrigin). Pass the staff tip (p.x + 18·facing) for anything that should start in front.

Advanced: who owns the lifetime of a custom effect

Anything an onCast starts with runAttack lives on the engine's Scheduler, so it is cancelled by clearWorld (map change) and on death. Anything it starts itself does not. Consecration uses a Phaser time.addEvent for its ticks, so it has to end itself. It checks currentMap() !== map and isDead() on every tick, subscribes to map:changed and player:died, ends on scene SHUTDOWN (added by the "Codex review fixes" commit), and keeps a module-level endActiveField so a second cast replaces the first field instead of stacking two. If you write a new persistent effect in onCast, either express it as a summon (the engine cleans up) or copy all four of those exits.

Combat math

ARCHITECTURE.md gives the damage formula for one hit line:

hit = matk × pct/100 × rand(mastery..1) × (1 + dmgAll + dmgElem) × elemMult × critMult × target.incomingDamageMult() − target.def.def   // min 1

The code in rollSkillDamage follows it term by term:

  rollSkillDamage(element: Element, damagePct: number, target: IMonster): { amount: number; crit: boolean } {
    const d = this.derived();
    const matk = num(d?.matk, 10);
    const mastery = clamp(num(d?.mastery, 0.5), 0, 1);
    const roll = mastery + Math.random() * (1 - mastery);
    const elemBonus = element === 'fire' ? num(d?.dmgFire, 0) : element === 'ice' ? num(d?.dmgIce, 0)
      : element === 'lightning' ? num(d?.dmgLightning, 0) : element === 'holy' ? num(d?.dmgHoly, 0)
      : element === 'shadow' ? num(d?.dmgShadow, 0) : 0;
    const def = target.def;
    let elemMult = 1;
    if (element !== 'neutral') {
      if (def.weak?.includes(element)) elemMult = 1.5;
      else if (def.resist?.includes(element)) elemMult = 0.5;
    }
    const crit = Math.random() < clamp(num(d?.critRate, 0), 0, 1);
    const critMult = crit ? 1 + Math.max(0, num(d?.critDmg, 0.5)) : 1;
    let incoming = 1;
    try { incoming = num(target.incomingDamageMult(), 1); } catch { /* ignore */ }
    const raw = matk * (num(damagePct, 100) / 100) * roll * Math.max(0, 1 + num(d?.dmgAll, 0) + elemBonus)
      * elemMult * critMult * incoming - num(def.def, 0);
    return { amount: Math.max(1, Math.round(raw)), crit };
  }

  • Player defence uses diminishing returns, not flat subtraction: damage × (1 − def/(def + 120)) (DEF_K, CombatSystem.ts:8). 120 def halves damage, and 240 def removes two thirds. A ±10% variance follows.
  • MP shield (Mana Shield, Ember Ward…) moves up to 95% of the hit onto MP, as long as there is MP to pay with. Both numbers are shown, stacked: purple HP, blue MP.

Statuses

A status is a timed condition on a monster. Spells carry a StatusSpec with three level functions: chance, durationMs and potency. When line 0 of a strike lands, combat.tryApplyStatus rolls the chance, checks immunity, converts the spec into a concrete StatusInstance, and hands it to monster.applyStatus. The monster then ticks it, slows or locks its AI, and tints itself.

  tryApplyStatus(target: IMonster, spec: StatusSpec, lv: number, element: Element, baseHit: number): void {
    if (!target || !target.alive || !spec) return;
    const chance = clamp(num(spec.chance(lv), 0), 0, 1);
    if (Math.random() >= chance) return;
    if (target.def.immune?.includes(spec.kind)) return;
    let duration = Math.max(0, num(spec.durationMs(lv), 0));
    if (duration <= 0) return;
    const isBoss = !!target.def.boss || target.def.behavior === 'boss';
    if (isBoss && (spec.kind === 'freeze' || spec.kind === 'stun')) duration *= 0.5;
    const rawPot = num(spec.potency(lv), 0);
    let potency: number;
    switch (spec.kind) {
      case 'burn':

      case 'curse': potency = clamp(rawPot, 0, 0.6); break;
      case 'chill': potency = clamp(rawPot, 0, 0.9); break;
      case 'shock': potency = Math.max(0, rawPot); break;
      default: potency = rawPot;
    }

  }

Advanced: status edge cases and the two boss rules
  • Bosses are protected from freeze and stun in layers. tryApplyStatus halves the duration for def.boss or behavior === 'boss'. Then Monster.applyStatus caps it at 2,500 ms for def.boss, so a 3,500 ms Judgment stun becomes 1,750 ms on the Lich Archon. Field bosses override applyStatus again: they cap the lock at 1,500 ms, refuse a new one while locked, and then ignore freeze and stun for 4 s (FieldBoss.ts:392), so they cannot be chain-locked. Bosses also skip hit-stun and knockback in takeDamage.
  • Immunity is checked twice, in CombatSystem and again in Monster.applyStatus. The second check keeps the monster safe even if a caller skips CombatSystem.
  • DoT ticks skip the damage formula. Burn and poison ticks call damageMonster with the stored potency, so shock, curse, weakness, crits and the monster's flat def do not change a tick. Those multipliers only matter once, through line 0's damage when the DoT is applied.
  • Ticks are accumulator-based (burnAcc, poisonAcc, Monster.ts:472). The monster's update clamps delta to 50 ms, and a while loop catches up any missed 500 ms ticks, so a slow frame never loses DoT damage. Each accumulator resets only when the status is newly applied, not when it is refreshed.
  • Locked monsters still tick. tickStatuses runs before the lock check, so a frozen monster keeps burning, and its other statuses keep counting down.
  • Status chance uses Math.random(), as does the whole engine. Nothing here is seeded or replayable. That is acceptable for an action game, but a balance simulator would need to inject an RNG.

Performance and extending the engine

Advanced: hot-loop performance

An ultimate fired into a full map can schedule hundreds of callbacks and simulate dozens of projectiles in sub-steps. The perf commit (0fdd88a) made the hot paths allocation-free:

  • Per-frame monster cache. live() builds the list of living monsters with their bounds at most once per game frame, keyed on game.getFrame() (AttackRunner.ts:118). Before that, every sub-step of every projectile called monsters.all() (two arrays) and getBounds() (one Rectangle per monster). Entries can die mid-frame because strikes resolve synchronously, so every loop still checks m.alive.
  • In-place compaction. The projectile list and the Scheduler's queue are compacted with a write index (projs[keep++] = p) instead of filter(). The Scheduler reuses its due buffer, and swaps it out while callbacks run because callbacks can schedule more work.
  • Pooled damage numbers from cached glyph atlases, capped at 90 alive.
  • The hit-VFX throttle described above.

What is still allocated: inRect builds and sorts a small array per area query, and rectC creates a Rectangle. These run once per strike, not per frame, so they were left alone.

Advanced: adding a new attack pattern safely
  1. Extend the contract. Add the name to AttackPattern in types.ts:126 (a lead-owned file), and any new options as an optional sub-object on AttackSpec, in the style of chain and rain, so all 130 existing specs still type-check.
  2. Add a run… method and a case in run(). Find monsters only through live(), frontNearest, nearestAny or inRect (never monsters.all()), and deal damage only through strike(). Then multi-hit, bonusVs, statuses, stacking and the VFX throttle all work.
  3. Schedule through this.sched, never scene.time, so map changes and death cancel the pattern. Anything persistent goes in projs (or a new list that clear() also empties).
  4. Define the VFX call for vfx.area (what x/y/targetX/w/h mean) and add it to ARCHITECTURE.md's "Skill engine semantics", because School authors write against that text.
  5. Check summon targeting. updateSummon picks the wake-up reach by pattern. A pattern whose reach is not range needs a branch there, as aoe_self has.
  6. Degrade gracefully. Every numeric field goes through num() with a sensible default, and a pattern with no target should still show something (the chain fizzle is the model).
  7. The attack-patterns chart groups by pattern name, so a new pattern appears there automatically.

Before adding a pattern, check whether onCast plus runAttack can build it from the existing seven. Flame Dash is a blink plus an aoe_self stretched over the path travelled, and Consecration is an aoe_self repeated on a timer. Neither needed engine changes.
