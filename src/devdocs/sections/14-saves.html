Saves, slots and migration

The whole game state that outlives a session is one plain object, the PlayerState, written as JSON to the browser's localStorage (a small per-site key/value store that survives reloads). src/systems/SaveSystem.ts owns it: creating a new character, the six save slots, reading and writing, and repair, which turns anything it finds in storage (an old format, a hand-edited value, half a corrupted string) into a valid state or reports the slot as damaged. The title screen's Character Select (src/ui/titleMenu.ts) is the only UI that works with slots directly.

The design goal is that a save is never the reason the game won't start. Every read is defensive, every write is wrapped, and repair falls back to a fresh character rather than throwing.

(types.ts:432.) Everything else is derived on load: max HP, matk and the other stats are recomputed from this (derived stats), monsters and drops are respawned, buffs start empty. Notice what the state refers to by id: the job, every skill, every item, the map and every quest. That is the root of the "ids never change" rule.

The two Phase 5 fields, merits and arenaBest, were added as optional so the type still describes saves written before them; repair fills them with 0. honors (Academy Honors) is optional too, but repair leaves it absent instead of filling it, because "no honors field" is how a legacy save is recognised and backfilled. version is still 1: no change so far has needed a format migration, only defaults.

The starting kit: a level 1 Apprentice on campus (START_MAP is mistvale, the original id of the Academy grounds), INT 10 / LUK 6 / STR 4 / DEX 4, Arcane Bolt level 1 on Q, 3 SP, 10 Red and 10 Blue Potions on keys 1 and 2 of both hotbar pages, the Oak Wand and Apprentice Robe equipped, and 50 mesos. fillVitals then sets HP and MP to the computed maximums. The title menu accepts names of 2 to 12 characters (letters, digits, spaces, -, _, '); the save layer itself only truncates to 16.

Six slots and the meta record

Phase 7 replaced the single save with six slots (one student each), MapleStory-style. The storage layout is documented at the top of the slot code:

// Storage layout (localStorage):
//   `${SAVE_KEY}:slot0` … `${SAVE_KEY}:slot5`  one envelope per slot: { format, savedAt, slot, state }
//   `${SAVE_KEY}:meta`                         SlotsMeta: last played slot + a cached summary per slot
//   `${SAVE_KEY}`                              legacy single save; migrated into slot 0 on first run and
//                                              kept as a backup until slot 0 is successfully re-written
//                                              (or the player deletes slot 0).
// The slot envelopes are the source of truth; the meta summaries are a cache (used to label a slot that
// has since become unreadable). The legacy exports (hasSave/loadSave/writeSave/deleteSave) act on the
// *active* slot, which the title screen sets before starting the game.

export const SAVE_SLOTS = 6;

(SaveSystem.ts:72.) SAVE_KEY is 'arcana-story-save-v1' (constants.ts:32), from the game's earlier title "Arcana Story". It was deliberately not renamed for The Academy, because renaming it would orphan every existing save.

Each slot holds { format: 1, savedAt, slot, state }. readSlotRaw also accepts a bare PlayerState (the shape older builds wrote), and requires at least a string name, a finite numeric level and a string job; anything less is an error ("Save data is corrupt", "Character data is missing") (SaveSystem.ts:153).

  • The active slot. A module-level activeSlot. The original single-save API (hasSave, loadSave, writeSave, deleteSave) kept its signatures and now acts on the active slot, so Progression's autosave and every other caller didn't change at all when slots were added.

/**
 * Persist into the active slot (Progression autosave / manual save / map change all land here).
 * Returns false when nothing was written (storage unavailable, quota exceeded, …).
 */
export function writeSave(state: PlayerState): boolean {
  ensureInit();
  const st = storage();
  if (!st) return false;
  const slot = activeSlot;
  const savedAt = Date.now();
  try {
    const raw = JSON.stringify({ format: SAVE_FORMAT, savedAt, slot, state });
    st.setItem(slotKey(slot), raw);
    const meta = readMeta() ?? emptyMeta();
    meta.slots[slot] = metaEntry(state, savedAt);
    meta.lastSlot = slot;
    if (slot === 0 && meta.legacyPending && st.getItem(slotKey(0)) === raw) {
      try { st.removeItem(SAVE_KEY); } catch { /* ignore */ }
      meta.legacyPending = false;
    }
    writeMeta(meta);
    return true;
  } catch (e) {
    console.warn('[save] write failed', e);
    return false;
  }
}

(SaveSystem.ts:325.) It returns whether the write happened; Progression.save() passes that on. The slot is written first, then the meta. Writing also makes this slot the "last played" one, which is how Continue knows where to go.

Advanced: repair invariants and trade-offs
  • Never throws. The whole body is in a try/catch that falls back to a fresh character. A save that can't be repaired at all therefore loads as a new level 1 student with the old name lost; the envelope-level checks in readSlotRaw (name, level, job present) exist so that a badly damaged slot shows as damaged instead of silently becoming that.
  • Repair runs more than once. listSlots repairs each slot to build its card, loadSlot repairs the chosen one, and the Progression constructor repairs its state again. It is idempotent (repairing a repaired state changes nothing), so this is wasted work but harmless. It does build a throwaway fresh character and compute derived stats each time; at six slots that is negligible.
  • Registry timing. Repair checks ids against the Registry. If skills or maps aren't registered yet (repair running unusually early), it keeps unknown skill and map ids instead of refunding or resetting them, so a load order slip can't wipe a build.
  • Lossy by design. An item, skill or quest the game no longer knows is gone after repair (skills at least refund their SP). The next save makes the loss permanent. That is acceptable for genuinely removed content and a disaster for a renamed id, which looks exactly like a removed one.
  • Failure modes of storage. If localStorage is unavailable (some private modes, blocked site data), storage() returns null: nothing is written and every slot reads empty. A full quota makes setItem throw, which writeSave catches and logs as [save] write failed, returning false; the game keeps running on the in-memory state. The automatic saves ignore the result, but the Esc menu's "Save Game" button checks it and logs "Saving failed" instead of "Game saved." (it used to report success unconditionally).

Migrating the legacy single save

Before slots, the game kept one save directly under arcana-story-save-v1. ensureInit migrates it the first time the slot code runs:

      // Migrate the pre-slots single save into slot 0 — only on a truly fresh slot store, so a lost
      // meta key never duplicates a character that was already migrated.
      const legacy = st.getItem(SAVE_KEY);
      if (!anySlot && legacy) {
        st.setItem(slotKey(0), legacy);
        if (st.getItem(slotKey(0)) === legacy) {
          meta.legacyPending = true;
          meta.migratedAt = Date.now();
          meta.lastSlot = 0;
          // … cache slot 0's summary in the meta
          console.info('[save] migrated legacy save into slot 1');
        }
      }

(SaveSystem.ts:192; "slot 1" is the player-facing, 1-based number of slot 0.) The legacy value is copied verbatim, a bare PlayerState, which readSlotRaw accepts. The original key is kept as a backup while legacyPending is set, and removed only when writeSave has written slot 0 and read the same bytes back, or when the player deletes slot 0.

Advanced: why the migration is shaped this way
  • Only on a fresh slot store. Migration runs only when there is no meta record and no slot has data. If the meta key alone were lost later, the scan rebuilds it from the slots instead of copying the legacy save in a second time.
  • Verify before trusting. Both the copy and the backup removal compare what was written with what is read back, so a quota failure halfway can't lose the only copy.
  • The meta is rebuilt, never required. If the meta is missing or malformed, readMeta returns null and init reconstructs summaries from the envelopes; every reader treats the meta as optional.

Character Select

The title menu has three entry points: Continue (the last played slot, else the most recently saved readable one), Character Select (the six cards) and New Game (the first empty slot, or a "replace a student" picker when all six are taken). Each card comes from a SlotSummary:

  • A student card shows the slot number, "School of Fire" (or "Core Curriculum" before the declaration) tinted in the School's colour, the animated job sprite, the name, a line like "Lv 27 · Year 3 · Flamebinder", the map, play time and how long ago it was saved, plus a "Last" badge on the slot Continue would load (titleMenu.ts:293). The Year and School come from yearOfTier and SCHOOL_NAME.
  • A damaged card says "Damaged save", the reason, and "Was Mira · Lv 31" from the meta cache when it remembers who was there. It can't be played, only deleted (or replaced by New Game).
  • An empty card offers "Enrol a new student".

Deleting asks "Withdraw Mira?" with Cancel selected by default, so a stray Enter never deletes a student (titleMenu.ts:331). Quitting to the title saves first and reopens Character Select.

Advanced: Character Select safety rules
  • Never overwrite silently. begin() re-reads the slots before writing. If the slot chosen as empty now has data (another tab wrote it), it moves to another empty slot, or back to replace mode if none is left (titleMenu.ts:452).
  • Damaged slots stay put. They count as taken for firstEmptySlot, so New Game never writes over unreadable data without asking. They are preselected in replace mode because they are the least valuable thing to overwrite.
  • The title is a separate scene that never constructs Progression, so nothing can autosave into a slot while the player is choosing one.

Why ids never get renamed

Phase 4 turned "Arcana Story" into "The Academy": the Elder became the Headmistress, instructors became Professors, quests became Assignments. ARCHITECTURE.md is explicit that this was "a re-theme of names and text": the save key and all existing ids (skills, jobs, maps, items, NPCs, quests) stayed the same. That is why the code still says elder_maelis, scout_finn, mistvale, mesos and arcana-story-save-v1, and why the quest file opens with "every id is unchanged from Arcana Story so saves keep working". Even the rename of the old Lich side quest in Phase 6 changed only its name; its id is still q_maelis_archon.

The reason is the repair table above. An id that disappears from the Registry is indistinguishable from removed content, so a renamed item vanishes from bags, a renamed skill is refunded and unlearned, a renamed quest loses its progress (a renamed story step would even reopen the chain), a renamed map sends the student back to campus, and a renamed job demotes them to Apprentice.

Advanced: changing the save safely
  • Rename display text, never ids. Names and descriptions are free to change; ids are storage keys.
  • If an id really must change, add an explicit mapping in repairState that rewrites the old id to the new one in skills, hotbar, inventory, equipment and quests before the "unknown id" filters run, and keep it for as long as old saves may exist.
  • New fields should be optional on PlayerState (or always defaulted in repairState), as merits and arenaBest were. Repair starts from a fresh character and copies known fields one by one, so a new field that repair doesn't copy is dropped (or reset to whatever newPlayerState gives it) on every load. Add it to repair in the same change.
  • Format changes would bump SAVE_FORMAT in the envelope (or version in the state) and branch on it in readSlotRaw / repairState. Nothing has needed that yet.
  • Test with a real old save. Export a slot's value from the browser's storage panel before the change, load it after, and check bag, spells, hotbar and quest log.
