Art pipeline

Every texture the game draws is generated at runtime into a Phaser texture key such as player_cleric, monster_frost_bat or pxs_cm_ring_gold. What changed over the project's life is where the pixels come from. This section tells that story and then walks through each producer: characters, monsters, icons, VFX and (briefly) the world. Terms:

  • source sheet: a PNG from a freely licensed pack, loaded under a src_* key and never drawn directly.
  • palette swap: recolouring a sprite by mapping each source colour (or brightness level) to a new colour, so one sheet can serve many jobs or monsters.
  • ramp: an ordered list of colours from dark to light (e.g. the ice ramp 0x0c2456 → … → 0xffffff) that a palette swap maps onto.
  • integer scaling: drawing each source pixel as exactly k×k screen pixels with nearest-neighbour sampling, never a fractional size.
  • procedural fallback: the original Canvas2D painters, still in the code, used for any texture whose source failed to load.

From procedural to pixel

Phase 1: everything procedural. The first build had no image files at all. The original contract in ARCHITECTURE.md says "all art is procedural (Canvas 2D / Phaser Graphics → textures)". Characters were a chibi rig painted with paths and gradients (char/rig.ts, posed by char/poses.ts), monsters had a hand-written draw function each (drawSnail, drawLich… in monsterArt.ts), icons were vector glyphs with a dilated outline, and the world was painted from per-theme palettes (world/palettes.ts).

Phase 2: the 16-bit pixel pivot. The smooth look was replaced by SNES-era pixel art from free packs (ROADMAP phase 2, commits c6de896 for the pipeline, then one commit each for characters, UI, monsters, world and VFX). The pivot was written down as five rules (ARCHITECTURE.md:186), summarised:

  1. Gameplay code does not change. Pixel art is sliced, palette-swapped and scaled into the existing texture keys, frame layouts and animation keys. Player still plays player_<job>_walk; it never learned that the frames now come from a PNG.
  2. The procedural path stays as a fallback when a source image is missing.
  3. One pixel size: PIXEL_SCALE = 2 (constants.ts:37), nearest-neighbour everywhere (pixelArt: true and roundPixels: true in main.ts:30), never a non-integer scale. Far parallax layers may use a larger integer.
  4. Strict licensing and downloads treated as untrusted data (see Licensing and credits).
  5. Cohesion: readable silhouettes, 1 px dark outlines, element colours (fire reds/golds, ice cyans/whites, lightning violets/yellows, apprentice indigo).

The procedural code was not deleted. In every domain the pixel builder runs first and the procedural painter only fills keys that do not exist yet, so a 404 on one PNG degrades one texture, not the game.

flowchart LR
  PNG["public/assets/(domain)/*.png"] --> LOAD["BootScene.preload()<br>queueArtAssets"]
  LOAD --> SRC["src_* texture<br>(never drawn)"]
  SRC --> SLICE["slice frames<br>+ re-anchor feet"]
  SLICE --> SWAP["palette swap<br>(ramp per job / element)"]
  SWAP --> OUT["1 px outline<br>+ overlays"]
  OUT --> SCALE["integer scale<br>×PIXEL_SCALE (2)"]
  SCALE --> KEY["existing key<br>player_* / monster_* / w_* / pxs_*"]
  SRC -.->|"missing"| PROC["procedural painter"]
  PROC --> KEY

The order varies a little by domain: monsters recolour the whole source sheet before slicing, characters classify pixels before swapping, characters are not upscaled (see below), and world PNGs were sliced and recoloured offline so the game only scales them.

Manifests and loading

Each art domain lists its files in its own manifest under src/art/manifests/: characters, monsters, world, vfx, ui, holy and shadow (the shadow list is empty; Shadow VFX reuse the shared sheets). An entry is a texture key and a path under public/assets:

export interface AssetEntry {
  /** Phaser texture key; prefix with the domain, e.g. 'src_char_wizard_idle'. Use the `src_` prefix for raw source sheets. */
  key: string;
  /** Path relative to public/assets, e.g. 'characters/wizard/idle.png'. */
  path: string;
  type: 'image' | 'spritesheet';
  frameWidth?: number;
  frameHeight?: number;
}

export function assetUrl(path: string): string {
  return `${import.meta.env.BASE_URL}assets/${path}`;
}

(assets.ts:17). assetUrl prefixes Vite's BASE_URL, so the same code works at / in dev and under the GitHub Pages sub-path. ALL_ASSETS concatenates the seven manifests (186 entries today, about 1.5 MB of PNGs across the five asset folders) and queueArtAssets queues them all in BootScene.preload(); a failed file only logs [boot] failed to load. Generators read the pixels back with sourceImage(scene, key), which returns null for a missing key: that null is what switches a domain to its fallback. The world manifest is mostly generated from key lists (PIXEL_DECOR_KEYS, PIXEL_TOWN_KEYS, PIXEL_FX_KEYS, per-theme PIXEL_BG layer stacks), so adding a decor piece is one string plus one PNG.

The icon sheet is the exception to "BootScene loads it". iconDataUrl is synchronous and is called by the title menu before Phaser has loaded anything, so icons.ts loads ui/icons/rpg_icons_7soul1.png itself through an HTMLImageElement at import time. It is also in the UI manifest, which only warms the browser cache.

Palette swaps and ramps

There are four palette-swap techniques, each tuned to its source material.

WhereTechniqueWhy this one
Characters, char/pixel.ts:309 rampMap Every pixel is first classified (robe, hat brim, hat tip, hair, skin, trim, gem, keep). Each class's source colours are mapped in HSL onto a target base colour, keeping each colour's lightness offset from the ramp's base and half of its hue offset. One witch sprite must become ten job looks with different robe, hat, trim and gem colours, so the swap has to be per body part.
Monsters, monsterArt.ts:1836 gradientMap, hueShift Gradient map: normalise each filtered pixel's luminance over the sheet and map it onto a ramp. Hue shift: rotate hue, scale saturation and lightness. Both take a PixFilter (hue range, min saturation, luminance bounds) so only part of the sprite changes, and chain() combines them. A monster usually needs a whole new element identity (a brown bat becomes an ice bat), sometimes only on one part (the thunder drake's wings).
VFX, particles.ts:157 recolorCanvas Luminance rank: build a histogram of brightness levels and give each level the ramp entry at its percentile. Effect sheets are often mostly white; a plain luminance map would collapse them onto the ramp's white end.
Icons, icons.ts:1041 recolor Seven-stop ramp built from the spec's colour (and color2 for highlights); pixels darker than 12% luminance (the outline) are kept. Icons must match an IconSpec colour exactly while keeping their dark outline.

The ramps themselves are data. Monster ramps live in RAMP (monsterArt.ts:1868: ice, snowFur, void, lava, magma, crag, storm, thunder, arcaneFire); VFX ramps in RAMPS (particles.ts:142):

export const RAMPS = {
  fire: [0x4a0c06, 0x8f1a0a, 0xd93512, 0xff7a1a, 0xffb830, 0xffe27a, 0xfff6d8],
  ice: [0x0c2456, 0x1c55a8, 0x3a9ae6, 0x7fd6ff, 0xc2f0ff, 0xffffff],
  ltn: [0x220c58, 0x4f22c4, 0x9b5cff, 0xd6b4ff, 0xffe94d, 0xfffbe8],
  arcane: [0x1e0f5c, 0x4a1fc4, 0x8f55ff, 0x5ee0ff, 0xb8f6ff, 0xffffff],
  gold: [0x6a3a00, 0xb57a0c, 0xffc933, 0xffe066, 0xfff3b0, 0xffffff],
  white: [0x5c5c5c, 0x9a9a9a, 0xcfcfcf, 0xf0f0f0, 0xffffff],
} as const;

Because the source packs use small palettes, every technique produces a small palette too: no technique invents a new shade per pixel, which is what keeps recoloured sprites looking hand-pixelled rather than filtered. World art is different: its theme recolours were done offline (the PNGs in public/assets/world are already sliced and swapped), and world/palettes.ts now serves the procedural fallback painters plus the TK texture-key scheme (w_<theme>_lip, w_<theme>_soil…).

Integer scaling and outlines

Foreground art is drawn at PIXEL_SCALE = 2 with imageSmoothingEnabled = false. The deliberate exceptions, all integers:

  • Characters are 1:1 (CHAR_SCALE = 1, char/pixel.ts:21). The Foozle mages are about 60 px tall at native size, already the on-screen target; ×2 would make the player roughly twice the height of its 26×58 hitbox.
  • Bosses are ×3 or ×4 through a per-monster scale (the Lich Archon and the Mossback Matriarch ×4, the Frostfang Alpha ×3).
  • Parallax layers use k of 2–4 per layer in PIXEL_BG.
  • VFX pick a scale with pxEven(targetPx, framePx): the nearest multiple of PIXEL_SCALE between 2 and 6 that brings the frame near the requested size.

Outlines are added only where the source has none. Characters get a 4-neighbour 1 px ring in a very dark version of the robe colour, stopped at the feet row so feet stay on the ground line (char/pixel.ts:464). Monsters get one when their spec sets outline (the ember imp and lava salamander), via a 1 px border added around each cut frame so the ring has room (monsterArt.ts:2118). All of this happens at 1× before scaling, so the outline is exactly one source pixel wide on screen.

Characters

One CC0 sprite, Foozle's "Pointy Hat Mage" (seven sheets: idle, walk, jump, attack, climb, hurt, death), becomes every job. A second, "Purple Mage", is used for the two old sage NPCs (Headmistress Maelis and Bram; npcBase matches their ids). The pipeline in char/pixel.ts, per frame:

  1. Re-anchor each source frame into an 80×80 cell with the body centred (found from torso colours) and the feet on a fixed row.
  2. Classify every pixel (pixel.ts:223). The red cloth is the robe, except red pixels surrounded by skin (the mouth) and red pixels flood-filled from the blue hat tip above the collar (the hat brim). Hair-coloured pixels near the bottom are boots and are kept.
  3. Palette-swap each class with rampMap toward the job's CharacterLook (robe, hat, trim, hair, skin, gem), cached per look.
  4. Decorate by tier (decorateHat): a metal hat band along the tip/brim seam, a diamond gem in the band from deco 3, side and centre crown spikes at deco 4.
  5. Outline, and for tier 4 an aura: a second, 8-neighbour ring in the hat-trim colour at alpha 150.

Tier maps to decoration in characters.ts:83:

/** Player decorations by job tier: band (1–2), circlet gem (3), crown + aura (4). */
function playerOpts(tier: number): PixelOpts {
  return { deco: Math.max(2, Math.min(4, tier)), aura: tier >= 4 };
}

So Years 1 and 2 share the plain band, a Year 3 job adds the gem, and a Year 4 graduate wears a crown and glows.

Frame layout. The pixel sheet's animations are listed in PIXEL_PLAYER_ANIMS (pixel.ts:37): idle 8 frames, walk 10, jump 2, fall 2, climb 4, prone 1, cast 6 (380 ms total), hit 4, dead 4, picked out of the source sheets (prone is a death frame, cast skips two attack frames). The procedural rig uses 64×80 frames and a different layout (FRAME_LAYOUT from poses.ts); ensurePlayerTexture remembers which path built a sheet and creates the matching animations. Either way the animation keys are player_<job>_<anim>, which is all Player uses.

On-demand sheets. At boot only the Apprentice sheet is built; every other job is queued with scheduleIdle to build in the background on the Title screen. If a sheet is asked for before then, playerTextureKey builds it on the spot:

export function playerTextureKey(job: JobId): string {
  const key = texKey(job);
  if (sheetScene && !sheetScene.textures.exists(key)) ensurePlayerTexture(sheetScene, job);
  return key;
}

(characters.ts:117). ensurePlayerTexture also calls warmSchoolSoon, because whoever just selected or advanced to a job is about to cast that School's spells. NPC sheets (npcTextureKey, an 8- or 6-frame idle) and dialog portraits (portraitDataUrl: a 40×40 head-and-shoulders crop of idle frame 0, nearest-neighbour upscaled) use the same frame renderer with decoration chosen from the look's hatStyle.

Monsters

monsterArt.ts builds monster_<id> with frames named <anim>_<i> and animations monster_<id>_<anim> for idle, move, hit, die and (optionally) attack. Each monster has a PixelSpec in buildPixelSpecs() (monsterArt.ts:1912) that names its source frames, its recolour and options:

      idle: { frames: wizard(...range(0, 4)), rate: 7 }, move: { frames: wizard(...range(0, 4)), rate: 9 },
      attack: { frames: wizard(...range(5, 14)), rate: 15 } },

One source often serves several monsters: the Bestiary golem is both the magma golem (magma ramp) and the crag golem (crag ramp); the Sunny mushroom is the cap shroom, the thorn shroom (hue-shifted cap) and the Shroom Monarch field boss. paintPixelMonsterSheet (monsterArt.ts:2154) then:

  • recolours the whole source sheet once (cached per monster), cuts each frame at 1×, flips left-facing art so every texture faces right, adds the optional outline and stamps overlays: tiny hand-placed pixel maps (the Matriarch's flower crown, the Monarch's gold crown, the Wyrm's horns) anchored to the top of the head ('peak') or the snout ('front');
  • derives missing animations: hit is the hit (or idle) frame flashed white at 45%, then normal; die, when the pack has no death frames, fades the hit pose through alpha 1 → 0.7 → 0.4 → 0.15 → 0 under the Sunny Land poof;
  • sizes one cell to fit every frame symmetrically around the anchor with the feet MONSTER_FOOT_PAD = 2 px above the cell bottom, and draws each frame at ×scale;
  • records the idle frame's visible height and width (monsterVisual) so Monster can place its overlays above the art (which can be taller than the hitbox) and size the freeze shell to it.

Status overlays are shared textures built at boot by generatePixelFxTextures: monster_fx_* (ice shell, shard, stun star, spark, ember, snow, puff, orb, aura, glow), the field-boss attack textures boss_fx_*, and the coin and meso-bag drops. They are original 1× pixel maps scaled ×2 (aura ×4); Monster draws and tints them for burn, freeze, stun and so on (see Monsters).

On demand. Per-monster sheets are not built at boot. ensureMonsterTexture(scene, id) (monsterArt.ts:2466) is idempotent and never throws: it tries the pixel sheet, falls back to the procedural paintMonsterSheet, and registers the anims. The Monster constructor and MonsterManager.bindMap call it, so a map pays only for the monsters it spawns.

Icons

Skills and items describe their icon as data, an IconSpec (glyph, color, optional color2 and bg; bg set means "skill tile"). Two entry points turn it into pixels (icons.ts:778):

  • iconDataUrl(spec, size): a cached PNG data URL for the DOM UI.
  • iconTexture(scene, spec, size): the same canvas copied into a Phaser texture (icon_v<version>_…), used for drops.

Both go through iconCanvas, which tries the pixel path first. The pixel path maps each glyph to a list of candidate cells in the 7Soul1 sheet (135 icons in a 12-column grid of 34 px cells). ensureAssignments walks every skill and item in Registry order and gives specs that share a glyph different icons where possible: an untinted candidate is used if its identity colour (a saturation-weighted average) is within a perceptual distance of 200 of the spec colour, otherwise a tinted candidate recoloured to the spec (icons.ts:980). Skill icons get a banded, dithered tile with a bevel; item icons a hard 1-source-pixel drop shadow. The icon is drawn at the largest integer scale that fits (floor((S + 4) / 32)).

Until the sheet arrives, or if it fails, the procedural painter draws the glyph in a 32×32 design space with a dilated dark outline. When the sheet loads, loadSheet bumps iconVersion, clears every cache, runs the onPixelIconsReady callbacks and emits player:changed so the UI re-renders (icons.ts:913; the DOM side is in The DOM UI).

Particles and the pixel VFX kit

particles.ts provides three things every spell module builds on (see Skills for how VFX are called).

Shared white textures. px_dot (8 px), px_soft (32 px stepped disc), px_spark (16×4 streak), px_star, px_ring, px_smoke, px_shard (12×20 diamond), px_flare (64 px), plus fx_pillar, fx_circle and six fx_rune_*. They are painted on a 2 px or 4 px grid with stepped alpha and are white so callers tint them. These keys and sizes predate the pivot and did not change.

Sheet kit. PX_SHEETS (particles.ts:204) lists 43 animated sheets (pre-trimmed horizontal strips, or rectangles for the Emcee Flesher 16×16 sheet) with their frame size, fps and the palette variants to offer. pxFx plays one:

export function pxFx(scene: Phaser.Scene, id: string, x: number, y: number, o: PxOpts = {}): Phaser.GameObjects.Sprite | null {
  const v = o.v && pxHas(scene, id, o.v) ? o.v : undefined;
  const tk = texKey(id, v), ak = animKey(id, v);
  ensureSheet(scene, id, v);
  if (!scene.textures.exists(tk) || !scene.anims.exists(ak)) return null;
  const n = pxFrames(id);
  const s = scene.add.sprite(x, y, tk, 0);
  s.setScale(o.scale ?? PIXEL_SCALE).setDepth(o.depth ?? DEPTH.VFX).setOrigin(o.ox ?? 0.5, o.oy ?? 0.5);
  // …
  if (o.loop) {
    cfg.repeat = -1;
    if (o.randomStart && n > 1) cfg.startFrame = Math.floor(Math.random() * n);
  } else {
    s.once(Phaser.Animations.Events.ANIMATION_COMPLETE, () => { if (s.scene) s.destroy(); });
    // …
  }

(particles.ts:355). One-shots destroy themselves; loops persist until the caller destroys them (pxLoop parents the sprite to a container). Options cover scale, rotation, flip, additive blend, tint, fps or a total dur, delay and fade. Textures are pxs_<id>[_<variant>] and anims pxa_<id>[_<variant>], built lazily by ensureSheet on first use: 43 base sheets plus 25 variants would otherwise be about 70 canvases at boot. A null return is part of the contract: every caller keeps a procedural fallback.

Pixelizer. Spell modules still draw some textures with smooth canvas paths (rings, beams, runes). pixelizeCanvas(canvas, cell, opts) (particles.ts:47) re-paints the canvas as cell×cell blocks with the block's mean colour and alpha quantised to steps levels (default 4), drops blocks below cutoff (default 0.08), and can posterise colour or force hard silhouettes. autoCell picks 2, 4 or 8 px by texture size, and pixelizeTexture applies it to a Phaser CanvasTexture and re-uploads it.

World art, lazy generation, canvas reads

World. generateTileTextures runs generatePixelWorldTextures first, which integer-upscales the 1× source PNGs into the existing w_/d_/t_ keys (terrain kit regions per theme, 46 decor pieces, 28 town pieces, 19 ambient/portal FX), then the procedural terrain, parallax, decor, town and FX painters, which skip keys that exist. Parallax layers are drawn by the map loader from PIXEL_BG. Maps, themes and parallax are covered in World.

Lazy generation. Boot builds only what the Title and a new Apprentice need; player sheets, per-School VFX, monster sheets and particle sheets are built on first use or drained one unit per tick on the Title screen through src/art/lazy.ts (ensureOnce, scheduleIdle, defineSchool, lazyRegister). The rule for new code is "never assume a texture exists, ensure it". Each unit is wrapped in timed(), so performance.getEntriesByType('measure') shows gen:* entries. Details in Scenes and boot.

The willReadFrequently default. Nearly every step above reads pixels back with getImageData. Chrome warns when a canvas is read often without the willReadFrequently hint and keeps such canvases GPU-backed, which makes reads slow. Rather than touch every call site, main.ts patches getContext once before Phaser starts:

{
  const orig = HTMLCanvasElement.prototype.getContext as (this: HTMLCanvasElement, id: string, opts?: unknown) => RenderingContext | null;
  HTMLCanvasElement.prototype.getContext = function (this: HTMLCanvasElement, id: string, opts?: unknown) {
    if (id === '2d') return orig.call(this, id, { willReadFrequently: true, ...(opts as object | undefined) });
    return orig.call(this, id, opts);
  } as typeof HTMLCanvasElement.prototype.getContext;
}

Explicit options still win (they are spread last). Commit 8e0fb70 notes this silenced about 500 boot warnings. The WebGL context Phaser draws with is untouched (id !== '2d').

Advanced: invariants every art generator keeps
  • Keys and layouts are the contract. A generator may change how a texture looks, never its key, frame names or anim keys. Player frames keep feet near the bottom of the frame (pixel 80×80 cells; procedural 64×80 with feet at y = 78), monster frames keep feet 2 px above the cell bottom and face right; entities flip with setFlipX.
  • Idempotent, never throwing. Every builder checks textures.exists first and wraps its work in try; failures log and fall through to the procedural path or to a shared fallback (monster_fallback, drop_fallback, __DEFAULT for icons).
  • Work at 1×, scale last. Recolours, outlines and overlays operate on source pixels; only the final draw scales. Doing it the other way round would produce 2 px outlines and break the shared pixel grid.
  • Cache by content. Palettes are cached per JSON.stringify(look), icon canvases per glyph/colours/size, recoloured monster sources per monster. A second Phaser game gets fresh textures because lazy units are keyed per texture manager (WeakMap).
  • Pixel textures stay pixel. Do not set a texture's filter to linear or draw it at a fractional scale; the title backdrop even floors its scroll offsets to whole source pixels for the same reason.
Advanced: cost, and how to add art safely
  • CPU, not GPU. Generation is synchronous canvas work on the main thread. The expensive parts are per-pixel loops (classify, ramp map, outline, pixelize) over the source sizes, so the big wins came from building less (lazy units, on-demand monster sheets, lazy VFX variants) rather than from faster loops.
  • Adding a monster sprite: add the PNG to public/assets/monsters/<pack>/, a key to MSRC and an entry to MONSTER_ASSETS, then a PixelSpec with a grid(key, fw, fh, cols, ax, ay) slicer (anchor = body centre x and feet y inside the cell), a recolour and rates. Add a row to that folder's CREDITS.md. The procedural painter remains the fallback.
  • Adding an effect sheet: a manifest line in manifests/vfx.ts (or a School's own manifest), a PX_SHEETS entry with frame size, fps and the ramps to offer, then call pxFx and keep a fallback for null.
  • Palette choices. Pick a ramp whose darkest entry is dark enough to act as an outline; the character and icon swaps deliberately keep near-black pixels dark (darkOutline, the 12% threshold) so silhouettes survive any recolour.

Licensing and credits

The pivot's licensing rule is strict (ARCHITECTURE.md:198): only CC0 / public domain, CC-BY 3.0/4.0, OGA-BY, or an explicit "free for personal and commercial use" statement from the author. No NonCommercial licences, no sprites ripped from commercial games, no scraped sprite dumps of unclear origin. Downloads are untrusted data: each pack was downloaded into its own scratch directory, unzipped there, nothing in it was executed, and only the needed PNGs (and TTFs for the UI) plus the licence or readme text were copied into public/assets/<domain>/<pack>/. Each domain wrote its own CREDITS.md (asset, author, source URL, licence, use) and the lead merged them into /CREDITS.md. The per-domain files are still the runtime source for the graduation credits roll (The DOM UI), so they must stay valid Markdown tables with Author and License columns.
