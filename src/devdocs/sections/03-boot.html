Scenes and boot

This section follows a page load from the first line of src/main.ts to a character standing on a map, and back to the title screen. In Phaser, a scene is a self-contained state of the game with its own display list, cameras, input, timers and lifecycle methods (init, preload, create, update). The Academy has exactly three: Boot (load and prepare art), Title (backdrop and the DOM title menu) and Game (everything else). Only one runs at a time. Along the way it explains lazy art generation, the system that keeps boot short by building most textures on first use or in the background.

main.ts and the Phaser config

The entry point does three things: patches canvas creation, creates the game, and starts the gamepad bridge (main.ts:9).

{
  const orig = HTMLCanvasElement.prototype.getContext as (this: HTMLCanvasElement, id: string, opts?: unknown) => RenderingContext | null;
  HTMLCanvasElement.prototype.getContext = function (this: HTMLCanvasElement, id: string, opts?: unknown) {
    if (id === '2d') return orig.call(this, id, { willReadFrequently: true, ...(opts as object | undefined) });
    return orig.call(this, id, opts);
  } as typeof HTMLCanvasElement.prototype.getContext;
}

The getContext patch matters because the art pipeline creates hundreds of offscreen canvases and reads their pixels back (palette swaps, outlines, pixelization). Without willReadFrequently, browsers keep those canvases on the GPU and warn on every readback; the commit that added it notes it silenced about 500 boot warnings. Callers that pass their own options still win, because the spread comes after the default.

startGamepadBridge() (GamepadBridge.ts:83) polls the Gamepad API every animation frame (with a 16 ms setInterval watchdog for when requestAnimationFrame is throttled) and turns buttons into synthetic keydown / keyup events for whatever keys the actions are bound to. It starts before any scene and runs for the life of the page, so every scene, the DOM menus included, gets controller support for free (see Input).

BootScene: preloading the art

BootScene.preload() draws a progress bar, logs failed files instead of stopping, and queues every external image: 

  preload() {
    const { width, height } = this.scale;
    const bar = this.add.rectangle(width / 2 - 200, height / 2 + 40, 0, 10, 0xcfd8ff).setOrigin(0, 0.5);
    this.add.rectangle(width / 2, height / 2 + 40, 404, 14).setStrokeStyle(2, 0xcfd8ff);
    this.load.on('progress', (p: number) => bar.setSize(400 * p, 10));
    this.load.on('loaderror', (f: Phaser.Loader.File) => console.warn(`[boot] failed to load ${f.key} (${f.url})`));
    queueArtAssets(this.load);
  }

src/art/assets.ts is the whole pipeline. Each art domain lists its files in a manifest, an array of AssetEntry under src/art/manifests/; ALL_ASSETS concatenates them and queueArtAssets hands each to Phaser's loader: 

export interface AssetEntry {
  /** Phaser texture key; prefix with the domain, e.g. 'src_char_wizard_idle'. Use the `src_` prefix for raw source sheets. */
  key: string;
  /** Path relative to public/assets, e.g. 'characters/wizard/idle.png'. */
  path: string;
  type: 'image' | 'spritesheet';
  frameWidth?: number;
  frameHeight?: number;
}

export function assetUrl(path: string): string {
  return `${import.meta.env.BASE_URL}assets/${path}`;
}
// …
export function queueArtAssets(load: Phaser.Loader.LoaderPlugin): void {
  for (const a of ALL_ASSETS) {
    const url = assetUrl(a.path);
    if (a.type === 'spritesheet') load.spritesheet(a.key, url, { frameWidth: a.frameWidth!, frameHeight: a.frameHeight! });
    else load.image(a.key, url);
  }
}

That is 186 files, all loaded as plain images (no manifest uses spritesheet today; slicing happens in code). Loaded images are source textures under src_* keys and are never drawn directly. Generators read them with sourceImage(scene, key), which returns null if the file failed, and produce the game's real texture keys (player_<job>, monster_<id>, w_/d_/t_ world keys). A missing file therefore falls back to the procedural painter for that key instead of breaking boot (see Art).

BootScene: boot-time generation

Once loading finishes, BootScene.create() shows a line of text, waits briefly for web fonts and runs six generation steps, each isolated in its own try/catch:

  create() {
    const { width, height } = this.scale;
    this.add.text(width / 2, height / 2, 'Opening the Academy gates…', { fontFamily: 'Trebuchet MS', fontSize: '28px', color: '#cfd8ff' }).setOrigin(0.5);
    // Wait for web fonts (pixel UI/damage fonts), then let the text render one frame before heavy generation.
    const fontsReady: Promise<unknown> = (document as Document & { fonts?: FontFaceSet }).fonts?.ready ?? Promise.resolve();
    Promise.race([fontsReady, new Promise(r => setTimeout(r, 800))]).then(() => this.time.delayedCall(0, () => {
      const steps: [string, () => void][] = [
        ['particles', () => generateParticleTextures(this)],
        ['characters', () => generateCharacterTextures(this)],
        ['monsters', () => generateMonsterTextures(this)],
        ['tiles', () => generateTileTextures(this)],
        ['skills', () => generateSkillTextures(this)],
        ['vfx', () => registerAllVfx()],
      ];
      for (const [name, fn] of steps) {
        try { fn(); } catch (e) { console.error(`[boot] ${name} failed`, e); }
      }
      this.scene.start(SCENES.TITLE);
    }));
  }
  • The font race. document.fonts.ready resolves when the pixel fonts used by the UI and the damage-number atlases have loaded; the 800 ms timeout stops a slow or failed font from holding boot hostage. Commit 4a6606c shortened it from 1,500 ms and dropped a 30 ms delay to 0.
  • delayedCall(0) defers the heavy synchronous work to the next scene tick, so the "Opening the Academy gates…" text is actually drawn before the main thread is busy.
  • Each step is isolated. If monster art throws, the world, skills and VFX still build and the game still reaches the title; the failure is one console.error.

Lazy art generation

Generating a texture here means drawing into an offscreen canvas (slicing a source sheet, palette-swapping it, integer-scaling it, adding outlines) and registering the result with Phaser's texture manager. It is synchronous main-thread work. Before the Phase 8 performance pass, boot built every per-School VFX texture and every job's player sheet up front, "~250ms of synchronous canvas work before the Title scene" according to src/art/lazy.ts. The pass that introduced lazy generation records boot going from about 675 ms to about 350 ms (commit 0fdd88a), and ARCHITECTURE.md puts the remaining boot generation at about 40 ms. The rule it introduced is short: never assume a texture exists; ensure it.

Every unit of art can be built two ways, whichever comes first:

The core is ensureOnce (lazy.ts:20): run a generator once per texture manager, timed, and never throw.

export function ensureOnce(scene: Phaser.Scene, name: string, gen: Gen): void {
  const key = scene.textures;
  let done = doneByManager.get(key);
  if (!done) { done = new Set(); doneByManager.set(key, done); }
  if (done.has(name)) return;
  done.add(name);
  try { timed(name, () => gen(scene)); } catch (e) { console.warn(`[lazy] ${name} failed`, e); }
}

Around it, four helpers:

HelperDoes
scheduleIdle(scene, name, gen, front?)Queues a unit for the background. A setTimeout pump runs one unit per tick: the first after IDLE_START_MS = 250 ms (30 ms if queued to the front), then every IDLE_GAP_MS = 30 ms until the queue is empty. Already-built units are skipped.
defineSchool(name, gen)Remembers a School's generator so it can be warmed by name later.
warmSchoolSoon(scene, name)Moves that School to the front of the background queue. Never builds synchronously. Called by ensurePlayerTexture with the job's School, so selecting or advancing to a job warms its spells.
lazyRegister(name, gen)Returns a drop-in replacement for registerVfx whose wrapped functions call ensureOnce on their first play. After that the cost is one boolean check.

A School wires all of this in three lines; Fire, from fireVfx.ts:16:

function buildFire(scene: Phaser.Scene): void {
  genTextures(scene);
  generateFireSheets(scene);
}

/** Boot hook: textures/sheets are built on first fire VFX (or in the background while on the Title screen). */
export function generateFireTextures(scene: Phaser.Scene): void { scheduleIdle(scene, 'fire', buildFire); }

defineSchool('fire', buildFire);
const registerVfx = lazyRegister('fire', buildFire);

The boot step generateSkillTextures therefore only queues the five Schools; the module-level registerVfx shadows the core one, so every fire_* effect registered in that file builds Fire's textures before its first frame. In practice the background queue drains while the player is still on the Title screen, so the first cast in a School normally finds everything built.

Every generator is wrapped in timed (perf.ts:3), which records a performance.measure named gen:<unit>. To see what was built and how long it took: 

performance.getEntriesByType('measure')
  .filter(m => m.name.startsWith('gen:'))
  .map(m => [m.name, Math.round(m.duration)])
Expect gen:characters, gen:particles, gen:monsters and the gen:world:* steps from boot, then gen:job:<id> and gen:fire-style entries trickling in while the Title screen is up. A School entry that appears only when you first cast is a sign the background queue had not reached it yet.
Advanced: lazy generation invariants, edge cases and how to extend it
  • Idempotent and non-throwing. Every generator may run at any time, in any order, possibly while a map is live. It must skip keys that already exist and must not assume another unit ran first. A failure is a warning, and the fallback (procedural texture or the generic VFX puff) covers it.
  • Demand wins the race. If a cast arrives before the idle pump reaches its School, the cast builds it synchronously (a one-time hitch of that unit's gen: duration) and the queued entry later finds it done and does nothing.
  • The pump is a plain setTimeout. It is not tied to a scene, so it keeps running after the Title hands over to the Game scene; units still queued then build during play, one per 30 ms.
  • Keying is per texture manager, mostly. ensureOnce tracks completed units in a WeakMap keyed by scene.textures, and the file header says a second Phaser.Game "would start clean". Two pieces of state are global, though: the ready flag inside each lazyRegister closure (set after the first play in any game) and the queued set of unit names in scheduleIdle. With a second game on the page, its first School VFX would skip ensureOnce. Harmless today (one game per page), but worth fixing before anything creates a second game.
  • Adding a lazily built unit (a new School, a new monster family): put all its canvas work in one gen(scene) function that skips existing keys; register its effects through lazyRegister(name, gen); call defineSchool(name, gen) if a job should warm it; and from a boot hook, scheduleIdle(scene, name, gen) so it is pre-built on the Title screen. Anything that reads a texture outside a VFX function (a UI icon, a sprite) should call the matching ensure* first.
  • Other deferred work follows the same idea: the damage-number glyph atlases (about 9 ms) are built 300 ms after the Game scene starts rather than on the first hit (DamageNumbers.ts:209).

TitleScene

TitleScene.create() builds a moonlit pixel backdrop and puts the DOM title menu over it:

  • Two backdrops. The pixel version stacks the world pack's sanctum sky, mountains and ruins as TileSprite layers at integer scales (×3 sky, ×2 mountains and tower), adds additive tinted twins to lift the colors, a moon, twinkling stars, shooting stars and drifting motes. If any of the four key source textures is missing, it tears that down and draws the older procedural night scene instead.
  • No sub-pixel drift. update() sets each layer's tilePositionX = Math.floor((t / 1000) * speed), snapping to whole source pixels so slow layers never shimmer.
  • The menu is DOM. TitleMenu (src/ui/titleMenu.ts) owns Continue, Character Select over the six save slots (with per-slot Delete) and New Game with name entry. When the player picks a character it calls back with a PlayerState; the scene fades out for 420 ms and starts the Game scene with it (TitleScene.ts:67). The leaving flag ignores a second pick during the fade. See UI and Saves.
  • Music and volume. The audio object is the same getAudio() singleton the game uses; saved volumes are applied before title music is requested (it starts on the first user gesture).
  private startGame(state: PlayerState) {
    if (this.leaving) return;
    this.leaving = true;
    const cam = this.cameras.main;
    cam.fadeOut(420, 0, 0, 0);
    cam.once(Phaser.Cameras.Scene2D.Events.FADE_OUT_COMPLETE, () => this.scene.start(SCENES.GAME, { state }));
  }

GameScene lifecycle

Phaser creates each scene object once and reuses it. scene.start(GAME, data) calls init(data), then create(), then update every frame until another scene is started, which shuts down this one: Phaser destroys its display list, timers and tweens and emits SHUTDOWN. The constructor never runs again, so init must reset every per-run field (GameScene.ts:54): 

  init(data: { state: PlayerState }) {
    this.initialState = data.state;
    this.map = null;
    this.inputBlocked = false;
    this.transitioning = false;
    this.pendingDest = null;
    this.latched.clear();
    this.page = 0;
    this.castBuffer = null;
  }

create() builds the services, wires events, keys and settings, loads the saved map, exposes window.arcana and registers teardown for SHUTDOWN; it is reproduced in Architecture: the frame flow. The only way back to the title is Esc → Quit to Title, which saves and calls scene.start(SCENES.TITLE) (miscWindows.ts:116). That shuts the Game scene down and runs teardown(): 

  private teardown() {
    const s = this.s;
    try { s.progression.save(); } catch { /* ignore */ }
    for (const fn of [() => s.ui.destroy(), () => s.skills.clearWorld(), () => s.monsters.clear(), () => s.drops.clear(),
      () => s.npcs.clear(), () => this.pet?.destroy(), () => this.arena?.destroy(), () => s.player.destroy(), () => this.map?.destroy()]) {
      try { fn(); } catch (e) { console.warn('[game] teardown step failed', e); }
    }
    this.map = null;
    this.pendingDest = null;
    bus.removeAll();
    setServices(null);
    this.input.keyboard?.removeAllKeys(true);
    this.input.keyboard?.enableGlobalCapture();
  }

It saves first, so a crash in any later step cannot lose progress; then destroys each system in its own try/catch; then clears every bus subscription, the service locator and all Phaser keys, and restores keyboard capture in case a dialog had disabled it. Back on the title, the menu opens straight on Character Select with the slot just played (markReturnToSelect / consumeReturnToSelect in ui/session.ts).

Map changes: loadMapNow and changeMap

loadMapNow(mapId, portalId?) (GameScene.ts:142) swaps the map immediately: it clears every system's per-map objects, destroys the old map, builds the new one with loadMap, records state.mapId, sets the physics and camera bounds, places the player at the named portal (or the map's default spawn), re-binds every system, starts the map's music, emits map:changed and the area banner, and saves. The sequence diagram is in Architecture.

Everything else calls changeMap, which wraps that in a fade (GameScene.ts:99): 

  changeMap(mapId: string, portalId?: string) {
    if (!Registry.map(mapId)) { console.warn(`[game] unknown map ${mapId}`); return; }
    // A request during an in-flight fade replaces its destination (e.g. respawn mid-portal).
    this.pendingDest = { mapId, portalId };
    if (this.transitioning) return;
    this.transitioning = true;
    this.s.player.setControlEnabled(false);
    this.s.audio.play('portal');
    const cam = this.cameras.main;
    cam.fadeOut(220, 0, 0, 0);
    cam.once(Phaser.Cameras.Scene2D.Events.FADE_OUT_COMPLETE, () => {
      const dest = this.pendingDest ?? { mapId, portalId };
      this.pendingDest = null;
      this.loadMapNow(dest.mapId, dest.portalId);
      cam.fadeIn(320, 0, 0, 0);
      this.transitioning = false;
      this.s.player.setControlEnabled(!this.inputBlocked);
    });
  }

Advanced: scene lifecycle and map-change edge cases
  • Per-run state belongs in init or create. A field initialised only at its declaration (private nextPickupAt = 0) keeps its old value on the second run, because the object is reused. That is harmless for nextPickupAt (a time stamp) but would not be for a counter or a flag; new fields need a reset in init.
  • Teardown runs on SHUTDOWN only. Closing the tab does not shut scenes down, so the last save is whatever the autosave, the last map load or the last job advance wrote.
  • Several SHUTDOWN listeners. Besides teardown, wireKeys and wireSettings each register a once(SHUTDOWN) to unsubscribe from bindings and settings changes. Anything a run subscribes to outside the bus must do the same, or it leaks into the next run and calls into a torn-down scene.
  • During a fade handleInput returns early (transitioning), so no casts, portals or pickups; monsters and projectiles keep updating until the swap. setControlEnabled at the end respects inputBlocked, so a dialog opened mid-fade still has movement locked afterwards.
  • Destination replacement is what makes "respawn while a portal fade is running" land on campus, and it also means the last of several rapid arcana.warp calls wins. The fade callback reads pendingDest at completion time, not the arguments of the first call.
  • Unknown maps are rejected before any state changes; a save naming a removed map loads START_MAP instead (create()).
  • The camera follows with lerp 0.12 and a 40 px vertical offset (startFollow(s.player.sprite, true, 0.12, 0.12, 0, 40)), re-applied on every map load because placeAt teleports the sprite.
