Overview and tech stack

The Academy is a MapleStory-style 2D side-scroller in 16-bit pixel art where every character is a mage. It runs in the browser on Phaser 3 with Arcade physics, draws its windows and HUD as ordinary HTML on top of the game canvas, and synthesizes all of its sound live with the Web Audio API. This section is the map to read before anything else: what the game is, which tools it is built with and why, how to run it and poke at it from the console, where things live in src/, and the order in which to read the rest of these docs.

What the game is

You play a student at a magic school. Each job (the MapleStory term for a character class) is a school Year. Everyone starts in Year 1 as an Apprentice and learns the core curriculum. At level 10 you declare one of five Schools (Fire, Ice, Lightning, Holy or Shadow) with Headmistress Maelis. Years 3 and 4 deepen that School, and you reach each by passing a Year-end Exam (a trial quest given by your School's Professor). The story ends with your Final Thesis: defeating the Lich Archon (a level 48 boss) in the Arcane Sanctum, the Forbidden Wing, followed by graduation. Levels stop at 50 (MAX_LEVEL in constants.ts:19).

The level thresholds are JOB_LEVELS = { 1: 1, 2: 10, 3: 25, 4: 40 } (constants.ts:20); the jobs themselves are in src/data/jobs.ts. Each School has 32 spells (11 in Year 2, 11 in Year 3 and 10 in Year 4), with two ultimates in Year 4. Skill points come at 3 per level, so nobody can max everything and builds are choices (a Tome of Unlearning lets you respec a Year). The world is 11 maps: the campus (Academy Grounds), six field zones from Whisperwood (levels 1–8) to the Arcane Sanctum (45–50), the Trial Hall wave arena and three optional branch zones off the main road (Moonlit Marsh, Glacier Grotto and the Restricted Stacks). Five rare field bosses roam the field zones, one per zone from Whisperwood to Stormspire Peak.

The project started as Arcana Story and was re-themed in Phase 4. Ids were deliberately left alone so old saves keep loading: the town is still mistvale, the Headmistress is elder_maelis, a School is a Branch in the types, the save key is arcana-story-save-v1 and the debug global is window.arcana. When the UI says "Assignment", the code says quest; "Year" is a job tier; "Professor" is an NPC.

The game canvas and the UI overlay are siblings in one stage element (index.html:12):

    <div id="stage">
      <div id="game"></div>
      <div id="ui-root"></div>
    </div>
    <script type="module" src="/src/main.ts"></script>

Phaser creates its canvas inside #game and scales it to fit the window (Scale.FIT; see Scenes and boot). UIScaler in src/ui/scaler.ts keeps #ui-root at a logical 1280×720 and scales it to cover the canvas exactly, so UI code can use game-pixel coordinates. The overlay itself has pointer-events: none; only its children take clicks, so the game underneath still receives input (style.css:12).

Advanced: consequences of the stack choices
  • Two rendering worlds. Anything in the DOM is drawn after (on top of) the whole canvas, so a window can never sit behind a sprite, and a Phaser object can never sit above a window. World-anchored UI (name tags, boss bars, damage numbers) is therefore Phaser; screen-anchored UI is DOM. Picking the wrong side means fighting the scaler or the depth system.
  • Keyboard ownership is shared. Phaser captures gameplay keys globally, while DOM windows listen on window. When a text field is focused, the UI calls services().game.setInputBlocked(true), which disables Phaser's global capture so typing works (see Input).
  • Pixel art means integer scaling only. pixelArt: true and roundPixels: true are global, and PIXEL_SCALE = 2 (constants.ts:37) maps each foreground source pixel to 2×2 screen pixels. A non-integer setScale on pixel art produces uneven pixels; see Art.
  • Synthesized audio needs a user gesture. Browsers keep an AudioContext suspended until the first pointer or key press, so SFX before that are no-ops and the last requested music starts on unlock (AudioSystem.ts:3; see Audio).
  • Function-valued data. Skill and status specs hold functions of the skill level (damagePct: (lv) => number), so content files are TypeScript, not JSON. That keeps balance formulas next to the data, at the cost of not being able to load content from a server or diff it as data.

Running it

Node 18 or newer. From the repo root:

npm install
npm run dev          # Vite dev server on http://localhost:5199
npm run typecheck    # tsc --noEmit (same as npx tsc --noEmit)
npm run build        # tsc --noEmit && vite build  -> dist/
npm run preview      # serve dist/ locally

The port comes from server: { port: 5199 } in vite.config.ts. The handbook is at /guide.html and these docs at /devdocs.html. Add ?debug=1 to the game URL to draw Arcade physics bodies and velocity vectors (main.ts:20).

Once a character is in the world, GameScene puts a small cheat API on window.arcana (GameScene.ts:365). It is the fastest way to test anything that would otherwise take an hour of play: 

    const api = {
      s,
      levelTo: (n: number) => {
        // Clamp to MAX_LEVEL and stop if a pass doesn't raise the level (gainExp is a no-op at the cap).
        const target = Math.min(Math.floor(n), MAX_LEVEL);
        while (s.progression.state.level < target) {
          const before = s.progression.state.level;
          s.progression.gainExp(expToNext(before) - s.progression.state.exp);
          if (s.progression.state.level <= before) break;
        }
      },
      give: (itemId: string, qty = 1) => s.progression.addItem(itemId, qty),
      mesos: (n: number) => s.progression.addMesos(n),
      warp: (mapId: string, portalId?: string) => this.changeMap(mapId, portalId),
      job: (job: JobId) => s.progression.advanceJob(job),
      heal: () => s.progression.heal(99999, 99999),
      maps: () => Registry.maps().map(m => m.id),
      pet: (on?: boolean) => { const p = this.pet; if (!p) return false; p.setEnabled(on ?? !p.isEnabled()); return p.isEnabled(); },
      depth: DEPTH,
    };
    (window as unknown as { arcana: typeof api }).arcana = api;

A typical test of a Year 4 spell: arcana.levelTo(40), then arcana.job('cryomancer'), arcana.job('frostbinder'), arcana.job('glacial_sage'), learn the spell in the Spellbook (K), drag it to the hotbar and arcana.warp('stormspire_peak'). main.ts also exposes the Phaser game itself as window.game.
Advanced: debug hooks in production, and their sharp edges
  • Not gated. exposeDebug() runs in every GameScene.create(), including the published build, and ?debug is read with URLSearchParams.has, so ?debug=0 also turns physics debug on. Both are deliberate conveniences for a single-player game, not security boundaries.
  • arcana is rebuilt per run. It closes over the current services object. After Quit to Title the old object is torn down (setServices(null)), so an arcana reference kept from a previous run points at destroyed systems. Re-read window.arcana after starting a new run.
  • levelTo is clamped to MAX_LEVEL. It feeds gainExp one level at a time, caps the target at MAX_LEVEL (50) and stops as soon as a pass does not raise the level, so arcana.levelTo(51) or any larger number simply stops at 50 instead of hanging the tab. It still only goes up. A level-up while dead does not revive you either (Progression skips the HP/MP refill when dead).
  • Timings. Texture generation is measured with performance.measure; in the console, performance.getEntriesByType('measure').filter(m => m.name.startsWith('gen:')) lists what was built and how long it took (see lazy art generation).

The game in numbers

At the time of writing the Registry holds 174 spells (14 Year 1 + 5 Schools × 32), 27 monster types (6 of them bosses: the 5 field bosses and the Lich Archon), 11 maps, 73 items, 42 quests (13 of them the story_ questline), 9 NPCs and 16 jobs. About 44,000 lines of TypeScript sit outside src/devdocs/ and src/guide/; the largest folders are skills/ (about 13,400 lines, mostly VFX) and art/ (about 8,900).

The three pages

One Vite build produces three independent pages. Each has its own entry module, so the handbook and the docs never load the game, and the game never ships the docs.

PageEntryWhat it is
index.htmlsrc/main.tsThe game.
guide.htmlsrc/guide/main.tsThe Official Student Handbook for players: Schools, spells, zones, monsters, items, rendered from the same data modules the game uses.
devdocs.htmlsrc/devdocs/main.tsThese developer docs: HTML fragments from src/devdocs/sections/, with diagrams and charts drawn from the game's modules.

The three inputs are listed in build.rollupOptions.input (vite.config.ts:58). base: './' makes every asset URL relative, so the same dist/ works at https://minormending.github.io/the-academy/ or from any folder, and Phaser goes into its own chunk so a game update does not invalidate the browser's cached copy of the engine. Every push to main typechecks, builds and deploys all three (see Build and deploy).

Advanced: reading ARCHITECTURE.md without being misled

ARCHITECTURE.md is mostly append-only history: its first half describes Phase 1 and was not rewritten. A short "Current state" note at the top now flags the statements that have since been superseded, and the later phases (further down the same file) win:

  • "No external assets — all art is procedural" was replaced by the pixel-art pivot: art now comes from the packs in public/assets/, with the procedural painters kept only as a fallback.
  • "Specialise at level 10 into one of three trees" became five Schools in Phase 3 (Holy, Shadow) and the Year framing in Phase 4.
  • The create and update orders listed under "Frame flow" once predated the familiar and the Trial Hall; they now include PetSystem and ArenaSystem, matching the frame flow.
  • "Boot generates every procedural texture" (also the header comment of BootScene.ts) predates lazy generation; boot now builds only what the Title screen and a new Apprentice need (lazy art generation).

Reading order

  1. Architecture: the service locator, the contracts, the event bus and the frame flow. Everything else assumes these.
  2. Scenes and boot: how a page load becomes a running game, and why textures appear lazily.
  3. The gameplay core, in the order a frame runs it: Input, Player physics, Skills and combat, Progression.
  4. The content systems: World and maps, Monsters, Story and quests.
  5. Presentation and persistence: UI, Art, Audio, Saves.
  6. Build and deploy, then How it was built for the agent-team story.
  7. When you are ready to change something: Recipes (add a spell, a monster, a map, a School).
