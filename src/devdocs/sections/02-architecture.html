Architecture

The game was designed so that ten builder agents could write it in parallel without reading each other's code. That goal explains almost every structural choice in src/core/. There are five pieces of plumbing:

  • Contracts: one file, src/core/types.ts, that declares every data shape (a skill, a monster, a map…) and every service interface (IPlayer, ISkillSystem…). Modules depend on these interfaces, never on each other's classes.
  • A service locator: one object, GameServices, that holds the live instance of every service. GameScene builds it and hands it to every system.
  • The Registry: read-only lookup of content by id (Registry.skill('fire_fireball')).
  • A typed event bus: fire-and-forget notifications (monster:killed, player:levelup) that let one system react to another without a direct call.
  • The VFX registry: visual effects registered by string key and played with playVfx.

This section explains each piece, the ownership rules built on them, the order in which a frame runs, the main cross-system flows (map change, death, level up, monster death), and the conventions every module follows.

The service locator: GameServices

src/core/services.ts is ten lines. It stores one GameServices object in a module variable: 

let current: GameServices | null = null;
export function setServices(s: GameServices | null) { current = s; }
export function services(): GameServices {
  if (!current) throw new Error('services not initialised');
  return current;
}
export function maybeServices(): GameServices | null { return current; }

Advanced: why constructors must not call other services

GameScene.create() starts from an empty object, const s = {} as GameServices, and fills it field by field, passing the same object to each constructor. When Progression is constructed, s.player and s.ui do not exist yet. A constructor may store s and subscribe to the bus; it must not call s.player.x or s.progression.derived(). Real work happens later in bindMap, update or event handlers, when every field is set. This is ground rule 4 in ARCHITECTURE.md.

  • setServices(s) runs before UIRoot is built, so UIRoot (and anything it calls) can use services(), but s.ui itself is still undefined until its constructor returns.
  • Not every system is a service. PetSystem (Pip the familiar) and ArenaSystem (Trial Hall) are private fields of GameScene, added after the contract was frozen. Other code reaches the arena through its own module helper (getArena()), not the locator.
  • One game at a time. The locator is a module-level singleton. teardown() sets it back to null; any code that calls services() after Quit to Title throws, which is why callbacks that can outlive a run (timers, tweens, DOM listeners) use maybeServices() or are cancelled on SHUTDOWN.
  • Testing in isolation is possible because every field is an interface: a fake GameServices with stub objects is enough to drive one system.

The Registry

Every content module exports a plain array (MONSTERS, MAPS, ITEMS…), and src/core/registry.ts indexes them by id the first time anyone asks: 

function index<T extends { id: string }>(arr: T[], what: string): Map<string, T> {
  const m = new Map<string, T>();
  for (const x of arr) { if (m.has(x.id)) console.warn(`[registry] duplicate ${what} id ${x.id}`); m.set(x.id, x); }
  return m;
}
// …
function ensure() {
  if (_skills) return;
  _skills = index(ALL_SKILLS, 'skill'); _monsters = index(MONSTERS, 'monster'); _maps = index(MAPS, 'map');
  _items = index(ITEMS, 'item'); _jobs = index(JOBS, 'job'); _npcs = index(NPCS, 'npc'); _quests = index([...QUESTS, ...STORY_QUESTS], 'quest');
}

export const Registry = {
  skill(id: string) { ensure(); return _skills.get(id); },
  skills() { ensure(); return [..._skills.values()]; },
  skillsForJob(job: JobId) { ensure(); return [..._skills.values()].filter(s => s.job === job); },
  // … monster(s), map(s), item(s), job(s), npc, quest(s)
  /** Job lineage from tier 1 to `job` inclusive, e.g. [apprentice, pyromancer, flamebinder]. */
  jobLineage(job: JobId): JobDef[] { /* … walks JobDef.parent */ },
};
  • Lookups return undefined for unknown ids (except job(), which is non-null asserted). Callers check: GameScene.changeMap warns and returns for an unknown map, and create() falls back to START_MAP if a save names a map that no longer exists.
  • Duplicate ids warn, last one wins. Watch the console after adding content.
  • Normal and story quests share one index, so a story_ id and a q_ id are looked up the same way.
  • The list methods copy ([...values()]); filtering or sorting the result is safe.
Advanced: the Registry and import cycles

core/registry.ts imports skills/index.ts and six data/ modules, and all of those import core/ (types, constants, balance, often the Registry itself). So core is not a leaf: core ⇄ data and core ⇄ skills are cycles at folder level. They are safe because ensure() builds the maps on the first call, not at import time; by then every module has finished evaluating. Two rules keep it that way:

  • Never call Registry.* at the top level of a data or skill module (for example to build a derived table in a const). Compute such tables lazily or inside a function.
  • Never cache the arrays from Registry.skills() in a module-level variable during import; read them when needed.

The indexes are built once and never invalidated. Content is static for the life of the page; there is no hot-adding of skills or maps at runtime.

The ground rules that made parallel work safe, in short:

  1. Edit only the files you own; create new files only in your own namespace.
  2. Keep every exported name and signature of your stub; add exports freely.
  3. Code only against types.ts + Registry + bus + playVfx; never import another agent's concrete class.
  4. Constructors must not call other services (see above).
  5. Your files typecheck with zero errors; no new npm dependencies.
  6. Be robust: missing textures or data degrade gracefully, never throw in update.

The only concrete cross-owner imports allowed were a short list of shared helpers: iconDataUrl / iconTexture from art/icons.ts; playerTextureKey, playerAnimKey, npcTextureKey, portraitDataUrl from art/characters.ts; newPlayerState, loadSave, hasSave, writeSave, deleteSave from SaveSystem.ts; and getAudio() from AudioSystem.ts. Advanced: where today's code departs from the rule

The ownership rule was strict while agents worked in parallel; later phases relaxed it in a few places. Before you copy any of these patterns, know that they are exceptions:

  • ui/hud.ts imports MAX_INVENTORY_STACKS from systems/Progression.ts; ui/arenaPanel.ts imports getArena and tuning from systems/ArenaSystem.ts; ui/controlsWindow.ts imports the pad map from systems/GamepadBridge.ts; ui/creditsRoll.ts and ui/titleMenu.ts import save-slot functions beyond the original five.
  • scenes/TitleScene.ts imports applySavedVolumes from ui/miscWindows.ts (same owner, A8, so within the rule).
  • data/npcScripts.ts has a type-only import of Progression, so NPC scripts can use methods that are not on IProgression. Type-only imports vanish at runtime, but they still couple the script to the concrete class.
  • MonsterManager imports Monster, LichArchon and the field-boss classes directly. Both sides belong to A6, so this is allowed.

The safe way to need something new from another module is still the original one: if it is a stable, widely useful fact, put the type or constant in core/; if it is behaviour, add a method to the service interface and implement it in the owning class; if it is a one-off notification, add an event to GameEvents.

The typed event bus

src/core/events.ts wraps one Phaser EventEmitter in a class whose methods are typed by a single map of event names to payloads: 

export interface GameEvents {
  'monster:damaged': { monster: IMonster; amount: number; crit: boolean; element: Element };
  'monster:killed': { monster: IMonster };
  'player:damaged': { amount: number };
  // …
  'ui:banner': { text: string; sub?: string; color?: string };
}

class Bus {
  private ee = new Phaser.Events.EventEmitter();
  // … `wrapped`: original handler → its guarded wrapper, so `off` can find it

  /** One throwing listener must not stop the remaining listeners of the same event: log it and carry on. */
  private guard<K extends keyof GameEvents>(ev: K, fn: Handler<GameEvents[K]>, ctx: unknown, once = false) {
    const wrapper: Handler<GameEvents[K]> = (payload) => {
      if (once) this.unguard(ev, fn, ctx);
      try { fn.call(ctx, payload); } catch (err) { console.error(`[bus] listener for '${ev}' threw`, err); }
    };
    // … remember the wrapper
    return wrapper;
  }

  on<K extends keyof GameEvents>(ev: K, fn: Handler<GameEvents[K]>, ctx?: unknown) {
    const w = this.guard(ev, fn, ctx);
    this.ee.on(ev, w);
    return () => this.off(ev, fn, ctx);
  }
  // … once, off
  emit<K extends keyof GameEvents>(ev: K, payload: GameEvents[K]) { this.ee.emit(ev, payload); }
  removeAll() { this.ee.removeAllListeners(); this.wrapped.clear(); }
}

export const bus = new Bus();

A typo in an event name or a wrong payload field is a compile error. on returns an unsubscribe function, which is how windows and per-map objects clean up. The events, who emits them and who listens (found by searching the source):

Advanced: dispatch is synchronous, and other bus pitfalls
  • Handlers run inside emit. When Progression.loseHp emits player:died, every listener runs before loseHp returns, which may be in the middle of a monster's own update (a boss hazard tick). ArenaSystem documents this and only sets a flag, ending the run on its next update: "despawning that monster under its own feet breaks it." Follow that pattern whenever a handler would destroy objects.
  • A throwing handler is logged and skipped. bus.on and bus.once register a guarded wrapper, so when one listener throws, bus.emit logs [bus] listener for '<event>' threw and still calls the listeners after it, and the exception never reaches the emitter. (Originally the underlying emitter stopped at the first throw, which let one broken subscriber starve drops and respawns.) Monster.die() still wraps its emit in try/catch, and Progression and MonsterManager.onKilled guard their own monster:killed work, so a bad handler costs one log line rather than a half-finished death. Still catch errors in new handlers: the guard keeps the game running, but the failed handler's own work is lost.
  • Subscription order is construction order. For monster:killed, Progression (built first) gets EXP before DropManager spawns loot. Nothing depends on that today; do not start depending on it.
  • teardown() calls bus.removeAll(), so systems that subscribe in their constructor never unsubscribe themselves; the next run gets a clean bus. Code that subscribes outside a game run (for example, at module load) would be wiped too, so don't.
  • Adding an event is a contract change in core/events.ts: add the name and payload type to GameEvents, emit it from the owning system, and keep payloads small (ids and numbers, not whole state objects).

The VFX registry

Visual effects are functions registered under a string key. Skill data names keys (vfx: { cast: 'fire_fireball_cast', hit: 'fire_fireball_hit' }); the skill engine plays them without knowing what they draw (vfx.ts:9): 

export function registerVfx(key: string, fn: VfxFn): void {
  if (registry.has(key)) console.warn(`[vfx] duplicate key ${key} (overwriting)`);
  registry.set(key, fn);
}

export function hasVfx(key: string): boolean { return registry.has(key); }

/** Play a VFX. Missing keys fall back to a generic puff so nothing crashes. */
export function playVfx(scene: Phaser.Scene, key: string | undefined, o: VfxOptions): Phaser.GameObjects.GameObject | void {
  if (!key) return;
  const fn = registry.get(key);
  if (fn) return fn(scene, o);
  if (!warned.has(key)) { warned.add(key); console.warn(`[vfx] missing key "${key}"`); }
  const c = scene.add.circle(o.x, o.y, 10, 0xffffff, 0.8).setDepth(DEPTH.VFX);
  scene.tweens.add({ targets: c, scale: 2.5, alpha: 0, duration: 250, onComplete: () => c.destroy() });
}

A VfxFn receives a VfxOptions (position, facing, optional target point, area size, angle, groundY). One-shot effects clean themselves up and return nothing; persistent visuals (projectiles, auras, summons) return a game object that the engine moves each frame and destroys when done. Every key is registered once at boot by registerAllVfx() in skills/index.ts; per-School keys go through lazyRegister, which builds that School's textures on the first play (see lazy art generation). The full call conventions per pattern are in Skills.

The frame flow

GameScene (GameScene.ts:63) builds the services in a fixed order, then wires events, keys and settings, loads the saved map and fades in: 

  create() {

    const s = {} as GameServices;
    s.scene = this;
    s.game = this;
    s.audio = getAudio();
    s.progression = new Progression(s, state);

The order matters in a few places. Input is handled after the world update: a cast starts inside handleInput (tryCast spends MP, sets the cooldown and cast lock and starts the attack, buff or summon), and whatever it leaves running (projectiles, scheduled hit lines) is advanced by SkillSystem.update from the next frame on. Level up and job advance

Progression.gainExp loops while EXP covers expToNext(level), adding 3 SP and 5 AP per level, refills HP and MP (unless dead) and emits player:levelup once with the final level, however many levels were gained. GameScene plays the levelup VFX and sound; UIRoot shows the banner. advanceJob (from an NPC script or arcana.job) emits player:job; GameScene calls player.setJob(job), which swaps to that job's sprite sheet (building it if needed), and plays the job_advance effect.

Advanced: edge cases in the flows
  • Respawn during a portal fade. If you die while a fade is running, the respawn's changeMap(TOWN_MAP) replaces the pending destination instead of being dropped (pendingDest), so you never arrive at the portal's map dead.
  • EXP after death. A burn tick or an in-flight projectile can kill a monster after you die. Progression still grants the EXP but does not refill HP on a resulting level-up, so a level-up never revives you.
  • The first map load has no fade-out. create() calls loadMapNow directly and then fades in from black over 400 ms. Its map:changed is emitted after every system and UIRoot exist, so all subscribers see the first map too.
  • Saves happen on every map load (the last step of loadMapNow), on respawn(), on job advance and on teardown, plus Progression's autosave every 30 s (AUTOSAVE_MS).

Coordinates and conventions

  • World Y grows downward, and an entity's y is its feet, not its center. A monster's hit point is (x, y − h/2). The player frame is 64×80 with feet at the bottom center, and the physics hitbox is 26×58, bottom-aligned (constants.ts:15).
  • Physics numbers: GRAVITY 1500 px/s², base walk 200 px/s, base jump 560 px/s. Platforms reachable by jumping must be at most 90 px apart vertically and 120 px horizontally; otherwise add a rope or ladder (see Physics).
  • Draw order uses DEPTH (constants.ts:8), never a literal number:

Advanced: conventions that bite
  • Feet-based y with Arcade bodies. Arcade bodies are positioned by their top-left corner. Every entity converts between its feet y and the body's position; use placeAt(x, y) and the entity getters rather than writing sprite.y yourself.
  • NAMETAG (45) is below DAMAGE_TEXT (50) although it is listed after it, so damage numbers always cover name tags.
  • Projectile visuals are drawn pointing right (+x) at rotation 0; the engine rotates them to their heading. Summons face by scaleX sign. Mirroring by hand on top of that flips them twice.
  • Renaming an id (skill, item, map, quest, job) silently breaks every save that contains it. Add a new id and migrate in SaveSystem instead (see Saves).
