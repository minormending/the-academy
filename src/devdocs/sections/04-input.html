Input, bindings and gamepad

This section follows a key press from the browser to the code that acts on it. Three owners read the keyboard, and none of them hard-codes a key: every gameplay key is an action (an id such as jump, slot0 or inventory) and a binding maps each action to one numeric keyCode, the browser's old-style key number (81 for Q, 32 for Space). Bindings live in src/core/bindings.ts, are saved to localStorage, and can be changed while the game runs. A gamepad does not get its own input path: a small bridge turns stick and button state into the same keyboard events a player would type.

Along the way it covers the parts of GameScene that make input feel good: latched presses (a tap shorter than one frame still counts), the 24-slot hotbar split into two pages, and the cast buffer (a spell tapped during another cast fires as soon as the first one finishes). It ends with the player settings in src/core/settings.ts. Movement itself (what Left or Jump does to the body) is in Player movement and physics.

Who owns which input

The ownership split comes from the original team contract in ARCHITECTURE.md ("Frame flow"): each builder agent owned one area, so each area reads its own keys. The split still holds.

OwnerActionsHow it reads them
Player left, right, up, down, jump, jump2 Phaser Key objects polled in readInput() every frame; Jump and Left/Right taps are also latched from the key's 'down' event.
GameScene slot0–slot11, interact, pickup, hotbarPage Phaser Key objects with latched presses, read in handleInput(), which runs near the end of GameScene.update (after every service has updated, before the UI).
UIRoot skills, inventory, stats, quests, minimap, help, menu A plain DOM keydown listener on window; looks the key up with actionsForKey().

The default ↑ belongs to two owners at once. The Player uses it as up (grab and climb a rope) and GameScene uses it as interact (enter a portal, talk to an NPC), as in MapleStory. Phaser hands both owners the same Key object, because keyboard.addKey(code) returns the existing key when one is already registered for that code. That is why Player.destroy() skips removing the key bound to interact. When the player presses ↑ next to a rope, the Player updates first and grabs the rope; GameScene then sees isClimbing() and skips the portal/NPC check (GameScene.ts:311).

Persistence and load-time repair

The map is saved as { v: 1, map } under the localStorage key academy-bindings-v1 (bindings.ts:90). load() starts from the defaults and copies only values that are valid: 0, a bindable key, or that action's own default. Then it unbinds later duplicates, so a corrupt or hand-edited save can never leave two actions on one key. Any exception (storage blocked, bad JSON) falls back to the defaults.

Rebinding, swaps and the shared Up key

Assigning a key that another action already uses swaps the two: the other action takes over the old key of the action being rebound.

export function setBinding(action: ActionId, keyCode: number): BindResult {
  if (!ACTION_IDS.includes(action) || !isBindableKey(keyCode)) return { ok: false };
  const prev = map[action] ?? 0;
  if (prev === keyCode) return { ok: true };
  const displaced = ACTION_IDS.filter(b => b !== action && map[b] === keyCode && !canShare(action, b));
  map[action] = keyCode;
  const res: BindResult = { ok: true };
  for (const b of displaced) {
    // Only hand over the old key if it is itself bindable (Esc is reserved for the menu and never moves).
    if (prev && isBindableKey(prev) && !conflicts(b, prev)) { map[b] = prev; res.swapped = b; } else { map[b] = 0; res.unbound = b; }
  }
  persist();
  emit();
  return res;
}

Source: bindings.ts:158

  • Sharing. SHARE_GROUPS (bindings.ts:85) lists the pairs allowed on one key. There is one: ['up', 'interact']. Binding Up to a new key therefore never displaces interact.
  • Unbinding instead of swapping. If the old key cannot move (it was 0, it is reserved, or it would collide with a third action), the displaced action is left unbound and the result says so. The Controls window prints "… is now unbound."
  • The reserved Esc rule. UNBINDABLE (bindings.ts:93) holds Esc (27), the OS/meta keys (91–93, 224), the IME key (229) and the lock keys (20, 144, 145). Esc cancels a key capture and always opens the menu, whatever menu is bound to. If menu is moved off Esc and lands on a key someone else had, that action gets unbound rather than handed Esc (commit 1e80a33). load() still accepts 27 for menu because it is that action's default.
  • Reset. resetBindings() restores the defaults, deletes the stored key and notifies listeners.

Live rebinding and labels

onBindingsChanged(cb) (bindings.ts:182) registers a callback and returns its unsubscribe function. Each consumer re-reads the map when it fires:

  • Player.bindKeys() and GameScene.bindKeys() drop their old Phaser keys and 'down' listeners and create new ones for the current codes. GameScene also removes Phaser keys (and their browser capture) for codes no gameplay action uses any more, so an old key stops being swallowed by the canvas.
  • The HUD relabels the hotbar and page hint (hud.ts:229); the Controls window redraws itself.
  • UIRoot and GamepadBridge need no callback. They call actionsForKey() / getBinding() on every event or poll.

Text shown to the player must never spell out a key. Use keyLabel(getBinding(action)), which gives a short name: 'Q', 'Space', '↑', 'F5', 'Num3', or '—' when unbound (bindings.ts:230). Two helpers sit next to it. keyEventInit(code) builds the key/code strings for a synthetic event (the gamepad bridge needs these). eventKeyCode(e) reads a DOM event's keyCode and falls back to parsing e.code on browsers that leave keyCode at 0; it maps right-hand Shift/Ctrl/Alt to the left-hand codes.

Advanced: binding invariants and why legacy keyCodes
  • Invariant: one key, one action, apart from the up/interact pair. load() enforces it on read and setBinding() on write. Code that adds an action must keep both paths in step. A new pair that should share a key goes into SHARE_GROUPS, not into a special case.
  • Why numbers, not KeyboardEvent.code. Phaser's Key objects are indexed by legacy keyCode, so storing that number means every consumer can call keyboard.addKey(code) directly. The cost: keyCodes follow the active keyboard layout for letters and are deprecated in the DOM spec. eventKeyCode() covers the browsers that send 0.
  • Listener safety. emit() copies the listener set before it iterates and wraps each call in try/catch. A consumer can therefore unsubscribe from inside its own callback, and one broken listener cannot stop the others.
  • Module-level state. The map is loaded once, when the module is first imported. Tests or tools that change localStorage afterwards will not see the change until the page reloads.
  • UI keys never trigger browser defaults. UIRoot calls preventDefault() for any key bound to a window action, so a Spellbook bound to F5 does not reload the page (from the final QA pass, b2a181f).

Key names in dialog and quest text

NPC lines and quest descriptions are module-level string constants, written long before the player might rebind anything. They hold a token instead of a key: {key:action}. keyText.ts replaces those tokens when the text is displayed:

export function keyName(action: ActionId): string {
  const code = getBinding(action);
  return code ? keyLabel(code) : '(unbound)';
}

/** Replace every `{key:action}` token with the action's current key name. Unknown actions are left as written. */
export function keyText(text: string): string {
  if (!text || !text.includes('{key:')) return text;
  return text.replace(/\{key:([A-Za-z0-9]+)\}/g, (m, id: string) => (ACTION_IDS.has(id) ? keyName(id as ActionId) : m));
}

Source: keyText.ts:10

Example from Professor Voltis's script: "press {key:hotbarPage} to flip between them". The places that show text call keyText(): the dialog window, the quest log, the chat log and the area banners (in UIRoot). So the text is correct even after a rebind mid-session. An unknown token stays visible as written, which makes a typo easy to spot in play.

Latched presses

Phaser's usual check for "the key was pressed this frame" is Phaser.Input.Keyboard.JustDown(key), which reads the key's private _justDown flag. Phaser queues DOM key events and handles them in a batch once per frame. If a key goes down and up between two frames (a quick tap, a gamepad button flicked, or a dropped frame), Key.onDown sets _justDown = true and Key.onUp sets it back to false in the same batch. JustDown never sees the press, and the spell does not fire. Playtesting found exactly this: fast taps on a hotbar key were ignored (commit 6492f47).

The fix is to latch the press: listen to the key's 'down' event, which fires on every press however short, record the press in a set, and clear it only when game logic consumes it.

    const add = (action: ActionId) => {
      const code = getBinding(action);
      if (!code) return null;
      const k = kb.addKey(code);
      const fn = () => this.latched.add(k);
      k.on('down', fn);
      this.keyLatchers.push([k, fn]);
      return k;
    };
// …
  /** True once per physical press, even if the key was released before this frame. */
  private consumePress(k: Phaser.Input.Keyboard.Key | null): boolean {
    if (!k) return false;
    Phaser.Input.Keyboard.JustDown(k);
    if (!this.latched.has(k)) return false;
    this.latched.delete(k);
    return true;
  }

Source: GameScene.ts:211 and GameScene.ts:265

consumePress still calls JustDown so Phaser's own flag is cleared and cannot fire later. handleInput clears the whole set when input is blocked, during a map transition or while the player is dead, so a key pressed during a dialog never fires afterwards. The Player latches Jump the same way (jumpLatched) and also records Left/Right taps (tapDirLatched), so a tap shorter than a frame still turns the character around. See Player movement and physics.

Hotbar: held skills, one-shot items, two pages

The hotbar is PlayerState.hotbar, an array of HOTBAR_SIZE = 24 entries (types.ts:426). Each entry is a skill id, "item:<itemId>" or null. Twelve slot actions address HOTBAR_PAGE_SIZE = 12 entries at a time, so there are two pages. The hotbarPage action (default Tab) moves to the next page, wrapping around. setHotbarPage() emits hotbar:page, which the HUD listens to; game.hotbarPage() returns the current page.

    for (let i = 0; i < this.hotkeys.length; i++) {
      const key = this.hotkeys[i];
      const entry = hotbar[offset + i];
      if (!entry) { JustDown(key); continue; }
      if (entry.startsWith('item:')) {
        if (JustDown(key)) s.progression.useItem(entry.slice(5));
        continue;
      }
      const pressed = JustDown(key);
      if (!key?.isDown && !pressed) continue;
      const r = s.skills.tryCast(entry);
      if (pressed && r === 'busy') this.castBuffer = { skillId: entry, until: time + 350 };
      if (pressed && r !== 'ok' && r !== 'busy') {
        // … 'Not enough MP.' / cooldown / not learned / passive → ui:log, skill:fail, ui_error sound
      }
    }

Source: GameScene.ts:291, where offset = page × HOTBAR_PAGE_SIZE.

  • Skills repeat while held, as in MapleStory: while the key is down, tryCast runs every frame. Most frames it returns 'busy' (the cast lock is still on) or 'cooldown'. Those results are silent because pressed is false, so holding a key does not flood the chat with error messages. Only a fresh press reports a failure.
  • Items fire once per press. Holding 1 drinks one potion, not one per frame.
  • Empty slots still consume the latch (JustDown(key)). Otherwise a press on an empty slot would wait in the set and fire later, after something was dragged into that slot.
  • Interact (GameScene.ts:311): portal first (map.getPortalNear), then the nearest NPC. Skipped while climbing.
  • Pick up repeats while held, at most once every 110 ms (GameScene.ts:320).

The cast buffer

Every cast puts the player in a cast lock for the spell's cast time (450 ms by default, 150 ms for movement spells, shortened by castSpeed; see Skills). During the lock, player.isBusy() is true and tryCast returns 'busy'. A player who taps the next spell slightly early would lose that tap. So a fresh press that returns 'busy' is stored in castBuffer for 350 ms, and fired the first frame the player is free:

    // Buffered tap from the previous cast lock: fire it the moment the player is free (≤350ms window).
    if (this.castBuffer) {
      if (time > this.castBuffer.until) this.castBuffer = null;
      else if (!s.player.isBusy()) {
        const id = this.castBuffer.skillId;
        this.castBuffer = null;
        s.skills.tryCast(id);
      }
    }

Source: GameScene.ts:282

The buffer holds one spell, and the latest busy tap replaces any earlier one. It runs before the hotbar loop, so a buffered spell takes priority over a key that is merely being held. isBusy() is also true during hit-stun and while climbing a rope, so a tap in those states is buffered too. It fires only if the state ends within 350 ms.

A failed buffered cast (out of MP, on cooldown) is silent: its result is ignored, because the player already heard nothing at the moment of the tap and an error 300 ms later would be confusing.

Blocking gameplay input

While a dialog, a shop, the credits roll or a text field is active, gameplay keys must do nothing. UIRoot checks this every frame in syncInputBlock() (UIRoot.ts:350) and, when it changes, calls game.setInputBlocked():

  setInputBlocked(blocked: boolean) {
    this.inputBlocked = blocked;
    const kb = this.input.keyboard!;
    if (blocked) { kb.disableGlobalCapture(); kb.resetKeys(); } else { kb.enableGlobalCapture(); }
    this.s.player.setControlEnabled(!blocked && !this.transitioning);
  }

Source: GameScene.ts:118

disableGlobalCapture() stops Phaser from calling preventDefault on bound keys, so typing a name with Q or Space works in a text box. resetKeys() releases every held key, so the character does not keep walking after a dialog opens. The Controls window also blocks input while it waits for a new key, and restores the previous state afterwards.

Dozens of VFX functions call scene.cameras.main.shake() and .flash() directly. Rather than change every caller, GameScene wraps those two methods once, in wireSettings():

      const shake = cam.shake.bind(cam);
      const flash = cam.flash.bind(cam);
      cam.shake = (duration?: number, intensity?: number | Phaser.Math.Vector2, force?: boolean, callback?: Phaser.Types.Cameras.Scene2D.CameraShakeCallback, context?: unknown) => {

        if (a <= 0 && !callback) return cam;
        if (!force && cam.flashEffect.isRunning) return cam;
        cam.flashEffect.alpha = a;
        return flash(duration, red, green, blue, force, callback, context);
      };

Source: GameScene.ts:238

The settings are read at call time, so a change applies to the next shake without re-patching. Setting shake to off also resets any shake or flash already running.

Advanced: details of the camera patch
  • Callbacks still run. With the setting off, a call that passes a completion callback is not dropped. It runs at intensity 0 or alpha 0, so code waiting on the callback (a boss intro, for example) still continues.
  • Why the flash guard. Phaser's flash copies alpha into a private _alpha when it starts and restores it when it ends. Writing flashEffect.alpha while a flash is running would change that flash partway through, so the patch only sets alpha when a new flash will actually start.
  • Idempotent. The __academyFx flag on the camera makes sure the methods are wrapped once, even if wireSettings() runs again on the same camera.
  • Extending. A new screen effect (a camera zoom pulse, say) should take its strength from shakeScale() rather than add another setting. Players who turned shake off almost always want the other effects quieter too.

Gamepad bridge

src/systems/GamepadBridge.ts starts from main.ts, before any scene (main.ts:38). The browser's Gamepad API pushes no events for button presses, so the code has to poll it, reading navigator.getGamepads() on every animation frame. The bridge picks the first connected pad with the standard mapping (the browser's common button layout for Xbox, PlayStation and Switch Pro style controllers). It works out which actions are pressed, and dispatches a keydown or keyup on window for each action whose state changed. Each event uses the key that action is currently bound to:

  function dispatch(type: 'keydown' | 'keyup', binding: KeyBinding) {
    const event = new KeyboardEvent(type, {
      key: binding.key, code: binding.code, bubbles: true, cancelable: true, repeat: false,
    });
    // Phaser reads the legacy numeric fields; constructor support varies by browser.
    Object.defineProperties(event, {
      keyCode: { value: binding.keyCode },
      which: { value: binding.keyCode },
      [GAMEPAD_EVENT_FLAG]: { value: true },
    });
    window.dispatchEvent(event);
  }

Source: GamepadBridge.ts:82

Deadzones. The left stick counts as pressed past 0.4 deflection. The right stick, which casts spells, needs 0.6, so resting a thumb on it does not fire anything. The pad has no input for slot10/slot11 (keys 1 and 2), where new characters keep their potions. A pad-only player has to drag potions onto a slot the pad can reach, or use the inventory.

Why a bridge and not a second input path

Every input feature already works on key events: latched presses, held-key repeats, the cast buffer, window toggles, the Esc rules, setInputBlocked, and rebinding. A separate pad path would have to copy all of them into Player, GameScene and UIRoot, and keep the copies in step. Because the bridge sends synthetic key events, none of that code knows a pad exists. And because it maps buttons to actions, not fixed keys, the pad follows the player's keyboard bindings for free.

Advanced: bridge edge cases and trade-offs
  • Polling cadence. Polling rides requestAnimationFrame. A 16 ms setInterval acts as a watchdog and polls whenever no animation frame has run for 32 ms or more, for example when the browser throttles rAF (GamepadBridge.ts:186).
  • No stuck keys. When the pad disconnects, a different pad becomes the first standard one, or the bridge stops, releaseAll() sends a keyup for everything it holds.
  • Typing. While an INPUT or TEXTAREA has focus the bridge sends nothing new (held keys stay held until focus leaves).
  • Event ordering and controlsClaimKey. A real key event passes through window's capture phase first, so the Controls window's capture listener can swallow it before UIRoot sees it. An event dispatched on window is "at target", and at-target listeners run in registration order, so UIRoot could see a pad's Esc before the Controls window does. UIRoot therefore asks controlsClaimKey(e) first (controlsWindow.ts:222).
  • Pad presses cannot be bound. Synthetic events carry __academyGamepad (GAMEPAD_EVENT_FLAG); the Controls window ignores them while capturing. Otherwise pressing A while rebinding would bind Space.
  • What the bridge cannot do. Everything is digital: there is no analog walk speed, no rumble, and pad buttons cannot be remapped separately from the keyboard. Unbinding an action on the keyboard also removes it from the pad (bindingFor() returns null).

The Controls window

src/ui/controlsWindow.ts opens from the Esc menu and from Help. It has two tabs:

  • Keyboard: every action in ACTIONS order, in four columns by group, each showing its key. Clicking a row starts a capture: input is blocked, and the window adds keydown/keyup listeners in the capture phase that call stopImmediatePropagation(), so neither Phaser, UIRoot nor the browser sees the key. The next bindable key goes to setBinding(), and a message reports any swap or unbind ("Spellbook → F5. Swapped: …"). Esc cancels; a key that cannot be bound shows an error. "Reset to defaults" calls resetBindings().
  • Gamepad: connection status (checked every 500 ms while open) and the GAMEPAD_MAP rows with each action's current key.

When not capturing, the window claims only Esc, and only when it is the topmost window, so Esc closes it instead of opening the menu behind it (controlsWindow.ts:118).

Advanced: adding a new rebindable action
  1. Add the id to ActionId and a row to ACTIONS (that also puts it in the Controls window), plus a default in buildDefaults(). A default that equals another action's key is unbound by load()'s duplicate pass, so pick a free key or add a share group.
  2. Read it where it belongs. Gameplay actions: create the key inside the owner's bindKeys() with a 'down' latch, and consume it with consumePress. If the action is a UI action, add it to the ui set in GameScene.bindKeys() so GameScene does not keep a Phaser key (and browser capture) for it, and to UI_ACTS in UIRoot.
  3. Optionally add a GAMEPAD_MAP row; the pad then follows the binding.
  4. Any text that mentions the key uses {key:yourAction} or keyLabel(getBinding('yourAction')).

The storage key stays academy-bindings-v1. Old saves load fine because load() starts from the defaults and only copies ids it knows.
