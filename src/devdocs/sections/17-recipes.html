Recipes

These are the common content changes, written as checklists. Each recipe names the files to touch, shows a real entry to copy from, and ends with a verify step. Most content in The Academy is data: plain objects in an exported array (FIRE_SKILLS, MONSTERS, MAPS, ITEMS…). The Registry (registry.ts) indexes those arrays by id, and every system looks things up through it. So adding an entry to the right array is usually enough for the spellbook, the minimap, drops, the handbook and these docs' charts to pick it up.

flowchart LR
  T["src/core/types.ts (contracts)"] --> D["data arrays: skills, monsters, maps, items, quests"]
  B["src/core/balance.ts (curves)"] --> D
  D --> R["Registry (by id)"]
  V["VFX keys (registerVfx)"] --> P["playVfx"]
  A["art: manifests + generators"] --> X["textures (ensured on demand)"]
  R --> G["game systems, UI, handbook, devdocs charts"]
  P --> G
  X --> G

Two habits make every recipe easier:

  • Copy a neighbour. Find the closest existing spell, monster or map and copy its shape. Every file uses small helpers (L, mk, plat…) that already encode the conventions.
  • Let the compiler list the work. Run npx tsc --noEmit early. Many lookups are typed Record<Element, …> or Record<School, …>, so a widened union makes every place that needs a new entry show up as an error.

Add a spell

A spell is a SkillDef (types.ts:190) in its School's file: src/skills/fire.ts, ice.ts, lightning.ts, holy.ts, shadow.ts, or apprentice.ts for the Year 1 core. Its visuals are VFX functions registered under string keys in the matching *Vfx.ts file. The spell names those keys, and the engine plays them through playVfx. See Skills for the cast flow and the seven attack patterns.

Checklist

  1. Pick the id and Year. The id uses the School prefix (app_, fire_, ice_, ltn_, holy_, shd_) and is snake_case. job decides the Year: e.g. pyromancer is Fire Year 2, flamebinder Year 3, inferno_sage Year 4. Each School has 11, 11 and 10 spells in Years 2, 3 and 4 now (Phase 9 grew the original eight per Year). The Phase 4 targets (3–4 attacks with different roles, 1–2 buffs or utility, 1–2 passives, a summon or field from Year 3, two ultimates in Year 4) are in ARCHITECTURE.md.
  2. Set kind to one of attack, buff, passive, movement or summon, and fill in the matching field (attack, buff, passive, movement, summon). For anything custom (heals, drains, dashes) use onCast and run the damage part with ctx.runAttack. If the effect outlives the cast (a trap, a channel, a ward), give it one of the School's lifetime helpers so it ends on map change, death and shutdown; see Phase 9: traps, combos, trades, dashes and channels.
  3. Level curves. maxLevel plus functions of level for mpCost, cooldownMs, damagePct, hits, maxTargets. Every tree file defines the same helpers: L(a, b, max) interpolates linearly from level 1 to max, Li rounds it, and K(n) is a constant (fire.ts:9).
  4. Tune against balance.ts (table below).
  5. Prerequisites. requires: [{ skillId, level }]. Keep chains shallow (see the pitfalls).
  6. Icon. icon: IconSpec, with a glyph from the IconGlyph union and colours. Each tree has an icon() helper that adds the School's tile background.
  7. VFX keys in attack.vfx (cast, projectile, hit, area), buff.vfx/auraVfx, summon.vfx or movement.vfxIn/vfxOut. Reuse the School's shared keys (fire_cast, fire_hit) where you can. Register new ones in the School's *Vfx.ts.
  8. Sound. sfx, usually the School's cast sound ('cast_fire').

Register its VFX

Each School's VFX file wraps registerVfx with lazyRegister, so the first time any of the School's effects plays, its textures are built first. From fireVfx.ts:22:

export function generateFireTextures(scene: Phaser.Scene): void { scheduleIdle(scene, 'fire', buildFire); }

defineSchool('fire', buildFire);
const registerVfx = lazyRegister('fire', buildFire);

Add your key next to the others in the School's register function (fireVfx.ts:1034):

export function registerFireVfx(): void {
  registerVfx('fire_cast', (scene, o) => { castFx(scene, o, o.scale ?? 1); });
  registerVfx('fire_cast_big', (scene, o) => { castFx(scene, o, 1.6 * (o.scale ?? 1)); });
  registerVfx('fire_hit', (scene, o) => { hitFx(scene, o.x, o.y, o.scale ?? 1); });
  registerVfx('fire_hit_big', (scene, o) => { hitFx(scene, o.x, o.y, 1.5 * (o.scale ?? 1)); });

  registerVfx('fire_arrow_proj', arrowProj);
  registerVfx('fire_burst_area', burstArea);
  // …

The return value matters. One-shot effects (cast, hit, area) clean up after themselves and return nothing. Persistent visuals (a projectile, an aura, a summon body) return a GameObject that the engine moves and destroys. A projectile visual is drawn pointing right, and the engine sets its rotation. arrowProj returns its container and falls back to procedural shapes when the pixel sheet (pxLoop) is missing. Copy that shape.

The spell needs no registration beyond its array. The spellbook lists a job's spells with Registry.skillsForJob(job) (registry.ts:29), and the handbook and the charts read the same data. In the console, check for [registry] duplicate skill id (id clash) and [vfx] missing key "…". The second means a key you named is not registered, and you see a white placeholder puff instead of your effect.

Add a monster

A monster is a MonsterDef (types.ts:306). Normal monsters are built with mk() in monsters.ts:80. mk() turns a short MonsterSpec (level, behaviour, size, multipliers) into full stats from the reference curves, so a monster's numbers follow the game's balance automatically. AI, statuses and spawning are covered in Monsters.

flowchart TB
  A["1. item: etc drop in items.ts"] --> B["2. mk() entry in monsters.ts"]
  B --> C["3. art: PixelSpec in monsterArt.ts"]
  C --> D["4. source sheet: manifest + public/assets + CREDITS"]
  B --> E["5. spawn entry in a map"]
  B --> F["6. optional: quest kill or collect"]
  E --> G["7. tsc, warp, fight"]

Checklist

  1. Its etc drop. Every mk() monster has a zone etc item. Add it to ITEMS with the etc(id, name, description, icon, sellPrice) helper, e.g. yeti_bone.
  2. The definition. Add a mk({…}) entry to MONSTERS in its zone's block. behavior is walker, hopper or flyer for normal monsters (bosses have their own classes). size is the hitbox. weak/resist take elements (×1.5 / ×0.5), and immune takes statuses.
  3. Art. Add a PixelSpec to buildPixelSpecs() in monsterArt.ts:1945: which frames of which source sheet make idle, move (and optionally hit, die, attack), plus a palette recolor. Reusing a loaded sheet with a new ramp is how most of the roster was made.
  4. A new source sheet (only if needed). Copy the PNG and its licence into public/assets/monsters/<pack>/, add a key to MSRC and an entry to MONSTER_ASSETS in manifests/monsters.ts, and add a row to public/assets/monsters/CREDITS.md and the Monsters table in CREDITS.md. Only CC0, CC-BY or OGA-BY art (see Art).
  5. Spawn it in a map's spawns (see Add a map) whose levelRange contains its level.
  6. Quest hooks (optional). Kill objectives name the monster id. Collect objectives name its drop. Example: q_finn_snails uses { kind: 'kill', monsterId: 'moss_snail', count: 10 }.

A real entry to copy, from monsters.ts:266:

  mk({ id: 'snow_yeti', name: 'Snow Yeti', level: 20, behavior: 'walker', speed: 70, size: { w: 56, h: 72 },
    hpMul: 1.05, expMul: 1.15, touchMul: 1.0, defMul: 1.2, weak: ['fire', 'shadow'], etc: 'yeti_fur', etcChance: 0.55,
    extraDrops: [{ itemId: 'yeti_bone', chance: 0.5 }] }),

And what mk() does with it (monsters.ts:80):

function mk(s: MonsterSpec): MonsterDef {
  const lv = s.level;
  return {
    // …
    hp: Math.round(refMonsterHp(lv) * (s.hpMul ?? 1)),
    exp: Math.max(1, Math.round(refMonsterExp(lv) * (s.expMul ?? 1))),
    mesos: mesosFor(lv),
    touchDamage: Math.round(refMonsterTouch(lv) * (s.touchMul ?? 1)),
    def: Math.round(lv * 0.4 * (s.defMul ?? 1)),
    // …
    aggressive: s.aggressive ?? true,
    // …
    drops: [
      { itemId: s.etc, chance: s.etcChance ?? 0.45, min: 1, max: 1 },
      ...potionDrops(lv),
      ...equipDrops(lv),
      ...(s.extraDrops ?? []),
    ],
  };
}

For the Snow Yeti that works out to: refMonsterHp(20) = round((12 + 5·20) × 220% × 3.5) = 862, × 1.05 → 905 HP; refMonsterExp(20) = round(expToNext(20) / 40) = 96, × 1.15 → 110 EXP; touch round(8 + 20·4.5) = 98; def round(20 × 0.4 × 1.2) = 10; mesos 53–86. Potion and on-level equipment drops come for free from the level brackets in potionDrops/equipDrops. ARCHITECTURE.md asks for multipliers of roughly 0.8–1.3, and the early zones deliberately sit lower (hpMul: 0.75 for the Moss Snail) because of the starting mastery roll.

Its art reuses the bestiary's wartaur sheet with a snow-fur ramp (monsterArt.ts:1994; the sheet is sliced by grid(MSRC.wartaur, 80, 80, 4, 48, 80) at line 1925: 80×80 cells, 4 per row, anchor at x 48 and feet at y 80):

    snow_yeti: { flip: true, recolor: gradientMap(RAMP.snowFur, { hue: [8, 48], minSat: 0.15 }),
      idle: { frames: wartaur(0, 2), rate: 2 }, move: { frames: wartaur(0, 1, 2, 3), rate: 7 } },
You can start without art. ensureMonsterTexture (monsterArt.ts:2588) tries the pixel spec, then the procedural painter. For an id with neither, paintMonsterSheet uses a generic fallback drawing. The monster is playable from the first commit and gets real art later.

Add a map

A map is a MapDef (types.ts:358) in src/data/maps.ts: size, platforms, walls, ropes, portals, spawns, NPC placements, a theme (art set) and music. MapLoader turns it into physics bodies and layered visuals (see World). The file has no runtime imports, so you can sanity check it with plain node.

Build it from the helpers at the top of the file (maps.ts:14):

const RESPAWN = 7000;
/** Field boss respawn after death (A6 jitters it ±20% → ~8–12 min). */
const FIELD_BOSS_RESPAWN = 600000;

const ground = (x1: number, x2: number, y: number): PlatformDef => ({ x1, x2, y, oneWay: false });
const plat = (x1: number, x2: number, y: number): PlatformDef => ({ x1, x2, y, oneWay: true });
const wall = (x: number, y: number, w: number, h: number): WallDef => ({ x, y, w, h });
/** Rope hanging from the platform at `top` down to just above the surface at `lowerY`. */
const rope = (x: number, top: number, lowerY: number): RopeDef => ({ x, top, bottom: lowerY - 8, kind: 'rope' });
const ladder = (x: number, top: number, lowerY: number): RopeDef => ({ x, top, bottom: lowerY - 2, kind: 'ladder' });
const portal = (id: string, x: number, y: number, targetMap: string, targetPortal: string): PortalDef => ({ id, x, y, targetMap, targetPortal });
/** Spawn across a platform's span (inset 40px from both edges). */
const on = (monsterId: string, p: PlatformDef, count: number, respawnMs = RESPAWN): SpawnDef =>
  ({ monsterId, x1: p.x1 + 40, x2: p.x2 - 40, y: p.y, count, respawnMs });
const span = (monsterId: string, x1: number, x2: number, y: number, count: number, respawnMs = RESPAWN): SpawnDef =>
  ({ monsterId, x1, x2, y, count, respawnMs });

Notice the tiers. The ground is at 1180 and the platforms step up 85 px at a time (1095, 1010, 925, 840, 755), each reachable by jumping. The next tier, 590, is 165 px above 755, so it gets a rope (rope(1060, M.y, K.y)).

Checklist

  1. Id and look. A new snake_case id. The id is save data: never rename it once shipped. Set theme to one of the existing MapThemes (town, forest, mushroom, snow, volcano, storm, sanctum; types.ts:349) and music to a MusicKey. A new theme means new terrain, parallax and decor art plus a THEME_RUNTIME entry (themes.ts:42).
  2. Geometry, following the design rules. The jump apex is about 105 px and a horizontal jump about 150 px, so: stacked one-way platforms reachable by jump must be ≤ 90 px apart vertically, otherwise add a rope or ladder, and horizontal gaps must be ≤ 120 px. The ground is one ground(0, W, G) spanning the map. A platform's y is its walking surface. A rope runs from the surface it leads onto (top) down to just above the lower one.
  3. Portals, both ends. A portal's targetPortal is the id of the portal you arrive at. For a two-way connection add one portal here and one in the neighbouring map, each naming the other. Whisperwood's east → shroom_hollow/west pairs with Shroom Hollow's west → whisperwood/east. One-way exits are allowed (the Sanctum's town portal arrives at the campus east portal, which leads elsewhere).
  4. Spawns. on(monsterId, platform, count) spreads monsters across a platform, inset 40 px from its edges. span(…) takes explicit x-ranges (use it on the ground, clear of portals). Keep monster levels inside levelRange.
  5. Register it in MAPS (maps.ts:381). That's all the minimap needs: it draws the platforms, name, region and level range from the current MapDef.
  6. Optional dressing. Hand-placed decor, waterfalls and a custom default spawn go in MAP_EXTRAS (mapExtras.ts:38). Without an entry the map uses its theme's seeded scatter.

Add a School

A School is an element, a three-job line (Years 2–4), 32 spells, a Professor, two Exams, staffs and a hall on campus. Unlike the recipes above, it changes contracts. Holy and Shadow were added exactly this way: first the lead's contract commit 7e70b18 ("Phase 3 contract: Holy and Shadow branches, jobs, poison/curse statuses, new glyphs/sfx, tree stubs"; see ARCHITECTURE.md "Phase 3"), then the trees (fdd90e1, 76abe50), the data re-theme with professors and exams (3c91190), and the campus halls (ccf1505). Advanced: pitfalls and how the code reacts
  • Renaming an id breaks saves. Saves store ids. When a save loads, SaveSystem.ts refunds the SP of unknown skill ids and clears their hotbar slots, resets an unknown job to apprentice, and sends an unknown map to the start map. Players lose progress silently. Rename the display name and keep the id: the Academy re-theme kept every id, and q_maelis_archon changed only its name. Lowering a skill's maxLevel is handled: the excess levels are refunded as SP.
  • Never assume a texture exists; ensure it. Art is generated lazily: a School's VFX textures on its first effect (lazyRegister), monster sheets on first spawn (ensureMonsterTexture), player sheets on demand. Code that does scene.add.image(x, y, 'fire_something') outside those paths can run before the texture is built. Register effects through the School's wrapped registerVfx, and call the matching ensure… before using a key. Keep a procedural fallback for a sheet that fails to load, as arrowProj does.
  • Keep requires chains shallow. ARCHITECTURE.md asks for 2–3 roots per Year, not one long chain. Cross-Year requirements are the sharp edge: the final QA had to lower Year-4 primaries from "Year-3 spell at level 10" to level 5 (81b17e1), because a fresh Year-4 student couldn't learn them. canLearn checks every entry, so a typo in a skillId makes a spell unlearnable without any error.
  • Stay in the balance bands. damagePct is per hit line, and the bands are per line too. A 3-line spell at the single-line primary value is three times too strong. Ultimates earn 800–1500% only with a long cooldown. Monster multipliers outside roughly 0.8–1.3 show up as outliers on the monster-HP chart. After a balance change, replay a Year: the pacing passes (49fcaad, e2126d0) found problems the curves alone didn't.
  • Duplicate ids don't fail. The Registry keeps the last entry and logs [registry] duplicate … id. registerVfx overwrites and logs [vfx] duplicate key. Both are only warnings, so read the console after every change.
  • Persistent VFX are the engine's to destroy. If a projectile or aura visual starts looping tweens, tie them to the object's lifetime (the lightning kit's loopWhileAlive exists because they leaked). Otherwise tweens keep running on destroyed objects after every cast.
  • Element bonuses need both halves. Adding dmgX to DerivedStats and to gear does nothing until CombatSystem.rollSkillDamage maps the element to it.
Advanced: doing a recipe with parallel agents

The recipes split along the ownership lines described in How it was built. A new School is the largest change. It parallelises the way Phase 3 did: the lead lands the contract, stubs and aggregator wiring in one commit. Then one agent owns src/skills/<school>*.ts and its public/assets/vfx/<school>/, another owns the data files (jobs, NPCs, scripts, quests, items), and a third owns campus art and the mistvale map entry. None of them edits types.ts. Run the typecheck after each agent reports, not only at the end: a missing Record entry in someone else's file is the signal that the contract and the work have drifted apart.
